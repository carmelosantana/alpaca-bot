# Alpaca Bot 0.6.0: the admin-wide panel, the MCP toolkit, and the 0.5 follow-ups

Wayfinding map: Kanboard #4364 (2026-09-15). Every decision below is a comment on a closed crux ticket, and the ticket is linked in the table. The prior direction was `2026-09-05-alpaca-bot-surfaces-and-extensions.md`, which is titled "1.1". Under the repo `CLAUDE.md` it means this 0.x line, and where the two differ, this spec wins.

## Why

0.5.0 rebuilt the plugin around one admin chat page. 0.6 gives it reach and hands. The chat follows the user onto every admin screen, taking that screen's context with it. The model can call the site's own WordPress Abilities and allowlisted remote MCP servers. And the sharp edges the 0.5 audit and reviews left open are closed first, so the new surfaces are built on them rather than beside them. The four security follow-ups (Kanboard #4330–#4333) were each deferred because they change behaviour or the wire, which only a minor may do. This is that minor.

## Changes

### 1. Groundwork

- **Namespace move.** `Rest\Errors` and `Rest\RateLimit` move to `AlpacaBot\Errors` and `AlpacaBot\RateLimit`, next to `AlpacaBot\Capability`. `Shortcodes\Chat`, `Abilities\Register`, `Toolkit\SummarizeToolkit` and the REST controllers already use both outside REST. Every docblock that names the old classes is updated in the same commit.
- **Hermetic integration suite (Kanboard #4322).** No test reaches `ollama.internal` or any network. The provider is stubbed the way the unit suite does it, or a test skips with a stated reason. The two `[#2977]` STDERR probes go. The output is pristine.
- **"Provider error:" only when the provider failed (Kanboard #4327, option a).** `Chat\Pipeline` keeps the prefix at the site where the provider threw. A run that ended in an error nobody announced, and a toolkit's `TerminationException('')`, each get their own plugin sentence with no prefix. Pinned in `tests/Unit/Chat/PipelineToolsTest.php`.
- **Bounded conversation migration (Kanboard #4335).** `Migrate04::migrateConversations()` keeps a per-row attempt count, so a row another plugin's filter makes unsaveable is retried a bounded number of times and then skipped, not re-run on every request.
- **`Chat\FakedToolCall`.** The faked-tool-call byte-range logic in `Pipeline`'s private statics (`recovered()`, `markup()`, `excisions()`, `answer()`) becomes one value helper with its own tests, and `Pipeline` delegates to it. Pure refactor, no behaviour change; the existing suite and the 21,957-input fuzz stay green.

### 2. Security follow-ups

- **Access settings model (Kanboard #4370).** A new `access` section in `Settings\Schema` holds one capability string per row:
  - `chat`;
  - `tool.web_fetch`, `tool.summarize`, `tool.draft_post`;
  - `tool.abilities`;
  - `mcp.<server id>`;
  - `settings.read`, `settings.write`;
  - `shortcode`.

  The value is validated against a fixed list of capabilities with friendly labels:
  - `manage_options`: Administrators
  - `edit_others_posts`: Editors and up
  - `publish_posts`: Authors and up
  - `edit_posts`: Contributors and up
  - `read`: any logged-in user

  Each row is the default its filter receives. `alpaca_bot/admin/menu_capability` and every chat `alpaca_bot/capability/{route}` take `chat`, and `Capability::filtered()`'s guard against `__return_true` and numeric returns stays as it is. The defaults reproduce 0.5 exactly, apart from the tool floor.
- **Tool floor (Kanboard #4331).** `Toolkit\Registry::enabled()` drops any toolkit whose row the turn's user fails (`user_can($userId, …)`, never the logged-in user) before `alpaca_bot/toolkits` runs, so that filter can still add or remove toolkits. A default site sees no change. On a site that opened chat to `read`, those users keep chat and lose the tools until an admin lowers a row. The changelog and the upgrade notice say so. The docblock's "a floor of enabled()'s own is a later 0.x release" and `docs/hooks.md`'s matching line are rewritten.
- **Settings read/write split (Kanboard #4332).** `GET /settings` and `/settings/schema` ask `alpaca_bot/capability/settings/read`, and `PUT /settings` asks `…/write`. Both default to the value of the existing `alpaca_bot/capability/settings` key, so no site breaks, and that key's own default comes from the `settings.read`/`settings.write` rows. `?reveal=1` keeps asking `manage_options` unconditionally. The Settings screen stays `manage_options` (options.php demands it).
- **Shortcode capability.** `Shortcodes\Chat::CAPABILITY` becomes the `shortcode` row, still asked of the viewer who triggers a generation. The docblock's "belongs to the admin-wide panel of a later 0.x release" is rewritten.
- **Distinct concurrency 429 (Kanboard #4333).** `StreamBudget`'s concurrency refusal gets its own code, `alpaca_bot_stream_concurrency`. The per-minute bucket keeps `alpaca_bot_rate_limited`. `chat.ts` reads the refusal reason on a failed redemption and says "you already have N streams open", not a generic error. `docs/api.md`'s 429 row is split.
- **web_fetch pinning (Kanboard #4330, #4371).** `WebFetchToolkit` resolves the host once, checks every resolved address with `SpecialPurposeAddress`, and pins the checked address into the connection through `http_api_curl` (`CURLOPT_RESOLVE`), on the first URL and on every redirect hop. Following redirects moves into the toolkit so each hop is resolved, checked and pinned. When `WP_Http` would not use cURL, the fetch is refused with a stated reason. A Site Health test reports whether web_fetch can run. The readme, the Tools help tab and the toolkit docblock replace "an egress policy is the supported mitigation" with what the pinning does and doesn't cover (a configured proxy resolves on its own).
- **The pinned egress factory.** One plugin class builds the Symfony HttpClient the MCP client is given: it has `resolve` pinned to an address that `SpecialPurposeAddress` has passed, redirects off, and timeouts and a response-size cap from settings. It shares the address check with web_fetch: one rule, two transports.

### 3. Front-end groundwork

- **`chat.ts` unit-testable (Kanboard #4334).** `boot()` is split into exported units (composer restore, stream redemption, notice rendering) tested under `node --test` with a DOM. The DOM devDependency goes through `/powerup:supply-chain` before it is added, and the Playwright specs stay. This lands before the drawer because the drawer reworks `chat.ts`.
- **Faked tool-call suppression while streaming (Kanboard #4329).** Only text from the opening marker onward is buffered, and a "calling a tool" state shows while the block is open. On `done` the block is replaced by the parsed result, or flushed verbatim if it never completed, so no text is ever lost. The empty-`delta` heartbeat before a tool call is kept. The new frame state is documented in `docs/api.md`.

### 4. The chat drawer (Kanboard #4365, #4369)

- **Classic screens.** `admin_footer` renders a launcher and an empty drawer on every wp-admin screen for a user who passes the `chat` row, except the plugin's own chat screen. Opening the drawer loads the chat fragment with one `hx-get` from a new `GET /view/panel` route (capability `chat`), and the chat bundle loads on first open.
  - **Budget:** until opened, the drawer adds no database queries and no chat bundle to a screen, measured with Query Monitor against the 0.5 baseline in `docs/reviews/2026-09-09-performance-baseline.md`.
- **Block editor.** A small `resources/ts/editor.ts` registers a `PluginSidebar` (`wp.editor`, 6.6+) built by `build.mjs` with the `wp.*` packages as externals. Nothing is bundled from `@wordpress/*`. It's enqueued on `enqueue_block_editor_assets` with `wp-plugins`, `wp-editor`, `wp-element` and `wp-data` as dependencies, and it mounts the same chat fragment. The post id comes from `core/editor`. The footer drawer is not rendered on the editor screen.
- **Context.** `Context\CurrentScreenSource` keeps supplying the post being edited, gated by `edit_post` for the turn's user.
  - It adds a screen label: the screen id and admin page title, rendered into the drawer server-side and sent back with the turn. It's treated as untrusted text: whitespace collapsed like the post title, and capped in length.
  - Both appear as chips above the composer. They're removable before sending and on by default.
  - Nothing else is sent: no list-table rows or queries, no option values.
- **Conversations and state.** The drawer and the chat page share one per-user conversation store, so a thread opened in one continues in the other. Open/closed and the active conversation live in user meta through `Chat\UserPrefs`. A turn keeps running on the server when the user navigates away (`Rest\Sse` sets `ignore_user_abort(true)`), and the drawer reopens on the conversation with the finished reply.
- **Settings › Access tab UI.** One row per capability key from §2. A row whose effective value a filter changed shows "set in code". MCP server rows appear once a server is added.

### 5. The abilities toolkit and our own abilities (Kanboard #4366)

- **`Toolkit\AbilitiesToolkit`.** An admin allowlist (Settings › Tools) of registered abilities from `wp_get_abilities()`, each exposed to the model as a tool whose schema is the ability's input schema.
  - Every call goes through `WP_Ability::execute()` as the turn's user, so the ability's permission callback, input validation and output validation apply.
  - Alpaca Bot's own `alpaca-bot/*` abilities are excluded, so a turn can't call a turn.
  - Descriptions come from other plugins and reach the model, so they're treated as untrusted: length-capped, and shown to the admin at allowlist time.
  - Gated by the `tool.abilities` row.
- **Tidying `Abilities\Register`.** It gets the three docblock corrections the research found:
  - the 7.0 range is `:619-634`;
  - `wp_ability_permission_result` exists only on 7.1+, not on the 6.9/7.0 floor;
  - the MCP Adapter ≥ 0.6.0 reads `meta.public` itself on 7.0 too, and honours `meta.mcp.public`.

  The annotations are reviewed and each one states what the core run route does with it.

### 6. The remote MCP client, plugin half (Kanboard #4366, #4368, #4371)

- **The contract.** php-agents 0.16 provides `McpServer`, `McpToolDefinition` (with `fingerprint()`), `McpClient` (with an injected HTTP client) and `McpToolkit` (allowlist of name to pinned fingerprint, withholding drifted tools). The contract is frozen by the php-agents session and posted on Kanboard #4364.
  - Alpaca Bot codes against it behind a plugin-side adapter interface with a test double, so its half is built and tested before the release.
  - The final step bumps `carmelosantana/php-agents` to `~0.16.0` and replaces the double with the real classes.
- **Settings › Tools › MCP servers.**
  - Add a server as a URL, an optional static header (name and value, typically `Authorization: Bearer …`), a prefix, a timeout and a response cap. The URL must be `https`, and it passes the same address check before it is saved.
  - The header value is stored like the provider API key: masked in `GET /settings`, revealed only through `?reveal=1` (`manage_options`), and never autoloaded.
- **Approval and pinning.** "Discover tools" lists the server's tools with their descriptions and annotations, and the admin ticks the ones to allow. Each approved tool's fingerprint is stored.
  - A tool whose live definition no longer matches is withheld from the model, and the server row shows "changed since approval: review".
  - Tools annotated destructive are shown with a warning and start unticked (annotations are untrusted hints).
- **Runtime.** Each allowed server becomes one toolkit in `Toolkit\Registry`, gated by its `mcp.<id>` row and built only for a user who passes it.
  - Tool names are `{prefix}__{name}`.
  - Calls use the pinned egress factory's client.
  - Every call is recorded with its arguments, and the result size goes into the usage receipt.

### 7. Release

`0.6.0` in `alpaca-bot.php`, `package.json` and `Plugin::VERSION`, in one commit with `readme.txt`'s `Stable tag`. The four header rows stay unless a floor moves (the repo `CLAUDE.md` rule). The changelog and upgrade notice lead with the tool floor's behaviour change and the settings key split. `docs/api.md` and `docs/hooks.md` are regenerated with their no-diff checks. Plugin Check runs against the built zip. The tag is pushed only on Carmelo's word.

## Constraints on the plan

- **Models:** all Opus for now: implementer, fixer and reviewer. Tickets carry `implementer_model: opus` and `reviewer_model: opus`, and every subagent dispatch passes `model: "opus"`.
- **TDD:** a failing test first. The gates are `composer check`, `bin/test-integration.sh`, `pnpm check`, `pnpm e2e`, `composer docs:hooks` and `composer docs:readme` with their no-diff checks, `bash bin/build-zip.sh`, and `bash bin/version-check.sh`.
- **Named review target: false load-bearing comments** (Kanboard #2978 comment 637). The house style puts the argument in the docblock, so every reviewer brief names both mechanisms:
  1. arguing from a counterfactual about the rejected alternative, or claiming a completeness the code doesn't have;
  2. a sentence silently falsified by a later change.

  Reviewers verify load-bearing comments against the file, a command run, or upstream source at its pinned version. Fixers re-read nearby sentences after adding a mechanism, and list the false sentences they caught in their own drafts. §2 of this spec rewrites several sentences that 0.6 falsifies on purpose ("a later 0.x release", the egress-policy disclosure).
- **Supply chain:** `/powerup:supply-chain` before any new dependency. The only planned ones are the DOM devDependency for §3 and the php-agents minor.
- **Board:** never set `approved_by` and never run `kanboard-run-milestone.sh`. Time is logged by hand in comments.

## Adopted defaults to confirm at spec review

These weren't grilled individually; each is the conventional answer, recorded on its crux:
- the drawer's screen scope, the shared conversations, and user-meta state (Kanboard #4369);
- the settings split's key names and back-compat (Kanboard #4370);
- the target namespace `AlpacaBot\Errors` / `AlpacaBot\RateLimit`;
- the per-row attempt count for Kanboard #4335;
- MCP header storage modelled on the provider key;
- destructive-annotated tools starting unticked, with no per-call confirmation in 0.6.

## Non-goals

- OAuth, STDIO, or MCP protocol features beyond `tools/list` and `tools/call` (the php-agents session owns the protocol).
- Hosting an MCP server of our own, or bundling the MCP Adapter (deprecated by the Adapter, PR #288).
- Per-call human confirmation, or the propose → diff → confirm → undo flow for mutating tools (the Site Actions add-on in the 2026-09-05 spec).
- Front-end chat (0.7), guest access, the Site Knowledge add-on.
- A role × capability matrix, or writing capabilities onto roles.
- Sending list-table data or option values as context.
