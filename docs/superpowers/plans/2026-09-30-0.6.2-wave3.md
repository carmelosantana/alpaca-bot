### Task 1: the raw WP-CLI write fails closed, reports like WP-CLI, and honours `--autoload`

`Cli\RawOptionWrite` (0.6.2 wave 2, #4695/#4696) takes over a raw `wp option update|set|patch|add alpaca_bot_settings` under WP-CLI. It arms from `before_run_command`, which reads the option name from the positional args, then `before_invoke:<command>`. The takeover itself is a `sanitize_option_alpaca_bot_settings` filter, guarded by `inCommand()`, which looks for WP-CLI's `Option_Command` on the call stack.

1. **Fail closed (priority, security).** When the option name is not on the command line, arming misses and the raw write goes round the schema. That skips #4539's key clearing and the MCP checks. It happens with `wp option update --prompt` (the name read interactively) and with positional defaults from `wp-cli.yml`. The takeover must recognise its own option without relying on argv. For example, the filter could be armed for every `option update|set|patch|add` invocation and decide from the `$option` argument core passes to `sanitize_option` (always `alpaca_bot_settings` for this hook). Or it could be registered whenever WP-CLI runs and gated by `inCommand()` plus the command being one of the four. Whatever you choose must:
   - never hijack a non-CLI write, a plain `update_option()` from a script, or `wp alpaca-bot settings`;
   - keep every existing disarm guarantee.

   Test it with a `wp-cli.yml` path (a temporary `wp-cli.yml` in the site's path that supplies the option name as a default, or `--prompt` fed from stdin) against real WP-CLI on ab061srv. Show it RED (the bypass) and then GREEN, and paste both. Add automated coverage where it can run in-process.
2. **"Unchanged" like WP-CLI.** Where WP-CLI itself would print `Value passed for 'alpaca_bot_settings' option is unchanged.`, the takeover must print the same. That includes a write the schema turns into no change, such as `30.0` versus `30`, or a value equal to what is stored once cleaned. Read the exact WP-CLI line from its source in the container. A write that changes a secret only is still reported as updated (#4696).
3. **`--autoload`.** A taken-over write currently ignores `--autoload`. The settings row must stay autoloaded (see Mcp\Secrets' and ProviderKey's docblocks for why), so refuse `--autoload=off|no|false` with a clear WP-CLI error that writes nothing. Accept `--autoload=on|yes|true` as a no-op. Either way, never ignore it silently. Read the assoc args through WP-CLI's runner, or whatever the hooks provide.
4. **An automated test of `inCommand()`'s true path**, so a WP-CLI rename of `Option_Command` turns a test red instead of silently failing open. For example: an integration test that loads WP-CLI's real `Option_Command` class from the phar or vendor copy, if it can be reached, and calls through it, or a unit test that builds a real call stack through a class of that exact name. It must fail if the class name the guard looks for no longer matches WP-CLI's. Justify how it proves that.

### Task 2: provider key display coupling, and the flush that must not happen

5. **Pin the non-flush.** Add a test on a real options table: store a fake key, set the `alpaca_bot_models` transient, then save an unrelated setting (e.g. `models.temperature`) that keeps the key. The transient must survive. It must fail if the row hook in Plugin.php busts unconditionally (check that with a mutation).
6. **Generic SECRETS loops call the provider-specific `ProviderKey::shown()`.** These are `Admin\Fields::display()`, `Rest\SettingsController::masked()` and `ChatCommand::settings()`'s dump. Either generalise the loops, e.g. a per-secret "is it held" resolver keyed by the field name, which fails loudly for a secret with no resolver, or make the coupling explicit (`Schema::SECRETS` documents that it holds exactly `provider.api_key`) with a test that fails if a second secret is added without a resolver. Prefer the generalisation if it stays small.

### Task 3: one shared write sequence

7. The sequence "MCP check → refusal, cleared MCP ids → provider key cleared by a move → `Store::replace()`" appears in three writers: `Rest\SettingsController::update()`, `Cli\ChatCommand::settings()` and `Cli\RawOptionWrite`. Pull it into one shared method, e.g. on `Settings\Store` or a small new class, that returns the refusal or the cleared facts. Each writer should keep only its own presentation: REST header and 400, CLI warn and fail, raw-write success line. This is only in scope if behaviour stays byte-identical. Every existing REST, CLI and raw-write test must stay unchanged and green, apart from mechanical wiring changes in construction. If the refactor would change behaviour, stop and report DONE_WITH_CONCERNS with what it would change, and do not commit it.
