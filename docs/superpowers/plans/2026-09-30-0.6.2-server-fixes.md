### Task 1: #4695 + #4696 — a raw `wp option update alpaca_bot_settings` goes through the schema and reports truthfully

**#4695.** `register_setting()`, and with it the option's sanitize callback, is hooked only on `admin_init` (`Admin\SettingsPage::register()`, `Plugin.php` around line 236). WP-CLI never fires `admin_init`, so a raw `wp option update alpaca_bot_settings '<json>' --format=json` (and `wp option patch …`, `wp option add …`) skips `Schema::sanitize()`. That bypasses type cleaning, #4539's rule that a `provider.base_url` move clears the key, and the MCP row checks. Task 3 of 0.6.1 made `wp alpaca-bot settings toolkits.mcp_servers` refuse a row it cannot keep (`Mcp\ServerSettings::check()`, `Mcp\WriteCheck`).

**#4696.** A raw option write that changes only the provider key stores it. `Settings\ProviderKey::beforeSave()` lifts it into `alpaca_bot_provider_key`, which leaves the row equal to the old row, so core's `update_option()` returns false and WP-CLI prints `Error: Could not update option` and exits 1. 0.6 already behaves this way for MCP header values (`Mcp\ServerSettings`).

**Ruling T1-a (what "done" means).** Under WP-CLI, a raw write of `alpaca_bot_settings` behaves like `wp alpaca-bot settings`:
- the value is cleaned by `Schema::sanitize()` over the stored settings, which includes #4539's rule;
- a `toolkits.mcp_servers` row the schema cannot keep, or an address the egress check refuses, fails the command non-zero with the same message REST gives, and writes nothing;
- a write that clears the provider key or an MCP header value by moving its URL prints a warning;
- a write that changed only a secret (the provider key or an MCP header value) exits 0 with a success line.

The mechanism is the implementer's to design. First read how WP-CLI's `option update` / `patch` / `add` decide success: the command source is in the harness container, and `wp cli info` gives the path. Candidates, weighed in the report:
- register the setting's sanitize callback outside `admin_init`;
- a `sanitize_option_alpaca_bot_settings` listener active under WP-CLI;
- a `WP_CLI::add_hook('before_invoke:option update', …)` that routes the plugin's own option through `Store`.

Two requirements hold whichever you pick:
- Keep one source of truth for the checks: reuse `ServerSettings::check()` and `Schema::providerKeyClearedByMove()`, never copy them.
- The settings page's own save path (options.php, `SettingsPage`'s callback with its notices) and REST must behave exactly as now; their existing tests stay unchanged and green.

If no mechanism can make #4696 exit 0 without hurting something else, stop and report NEEDS_CONTEXT with what you found.

**Tests.** Unit tests for the listener or hook logic. End to end against real WP-CLI on ab061srv, pasted into the report:
- a raw write that moves `base_url` clears a fake key, with a warning;
- a raw write carrying a refused MCP row exits non-zero, names the row, and stores nothing;
- a key-only raw write exits 0 and the key reaches `ProviderKey::resolve()`;
- a normal raw write still stores.

If a real-WP-CLI case can be automated in the integration suite (e.g. by invoking the command class in-process), do that too.

### Task 2: #4699 + #4700 — show "no key" when the key option is missing, and flush the model list on every key change

**#4699.** When the settings row holds `Schema::MASK` but `alpaca_bot_provider_key` is absent (a raw write, or the option deleted outside the plugin), the Provider tab, the REST masked read and the CLI dump all show the key as set, while nothing is sent. Every surface that shows "a key is set" must ask whether a key is actually held (`ProviderKey::resolve()` non-empty, or the equivalent), and show `''` / no key otherwise. That covers `Admin\Fields::display()` for the secret field, `Rest\SettingsController::masked()`, and `ChatCommand::settings()`'s dump. Keep the cost to one option read on the admin, REST and CLI paths only; the front end must still read nothing extra. Decide whether a move-clears-key notice (#4539's `providerKeyClearedByMove()`) should still fire when the row says MASK but no key is held. It should not claim to clear a key that did not exist, so fix that too and test it.

**#4700.** Saving `''` over a row that still holds a plaintext key, with no key option yet, changes the key the site uses (plaintext A → none), but `ProviderKey::beforeSave()` does not touch the option (`$key === $held`, both `''`) and the row hook busts only on `provider.kind` / `provider.base_url`. So the `alpaca_bot_models` transient (`Provider\ModelCatalog::TRANSIENT`) can outlive the key. Flush on that path too, and make the `Plugin.php` comment near line 117 (the one that says the model list is flushed whenever the key changes) exactly true. A test drives the path on a real options table.
