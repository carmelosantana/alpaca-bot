### Task 1: #4538 — confine what an allowlisted ability can run

**Problem.** `Toolkit\AbilitiesToolkit` offers the model only allowlisted abilities (`toolkits.abilities`), never `alpaca-bot/*`. An allowlisted ability that itself runs other abilities (the MCP Adapter's "execute any ability") reaches any ability, including non-allowlisted ones and `alpaca-bot/*`. 0.6.0 added a re-entrancy guard (`alpaca-bot/chat` and `alpaca-bot/summarize` refuse with `alpaca_bot_turn_running` while a turn runs); that stays. What is missing is the allowlist being enforced on nested executions.

**Ruling T1-a (mechanism).** While `AbilitiesToolkit::run()` is executing an ability, any ability execution that happens inside it (at any depth) is refused before it runs unless its name is on the effective allowlist: the stored allowlist as `allowed()` reads it (never an `alpaca-bot/*` name). The guard is installed immediately before `$ability->execute()` and removed in the same `finally` that restores the user, so it applies to nothing outside the call, and it nests correctly (a depth counter or stack, not a boolean).
- On WordPress 7.1+: a `wp_pre_execute_ability` filter at priority `PHP_INT_MAX` (last word, so an earlier short-circuit cannot let a refused ability through) that returns a translated `WP_Error` (code `alpaca_bot_ability_not_allowed`, message naming the ability) for a name not allowed, and returns `$pre` unchanged otherwise.
- On 6.9 and 7.0, where `wp_pre_execute_ability` does not exist: `wp_before_execute_ability` (fires after the permission check, before the callback, on 6.9+) must stop the nested ability running. An action cannot return a value, so it throws; verify and document what the outer call then answers on each version (6.9 has no catch around the callback; 7.0/7.1 wrap callback throws as `ability_callback_exception`, which `run()` already maps to SchemaTool's fixed text). The listener must not fire twice on 7.1 in a way that changes the answer (on 7.1 the pre filter refuses first, so `wp_before_execute_ability` never fires for a refused name — prove it).
- Core source for reference: WP 7.1.2 at `/home/carmelo/wp-env/wp-env-alpaca-bot-00213f3e/WordPress/wp-includes/abilities-api/class-wp-ability.php`; 6.9.1 at `/home/carmelo/Projects/JawpOS/jawpos/.wordpress/wp-includes/abilities-api/class-wp-ability.php`; 7.0.4 at `/home/carmelo/Updater/.restore/updater-dev-skeleton/site/wp-includes/abilities-api/class-wp-ability.php`. Read-only.

**Ruling T1-b (scope).** The ticket's other candidates — a Tools-tab warning on meta-abilities, and re-checking the token cap between tool iterations — are out of scope for 0.6.1. Confinement removes the reason for the warning; the cap re-check is a product change reported to the coordinator.

**Tests.**
- Unit: nested execution of a non-allowlisted ability during `run()` is refused and its callback never runs; nested execution of an allowlisted one runs; `alpaca-bot/chat` nested is refused even if a stored list names it; after `run()` returns (and after it throws) the guard is gone (a direct `execute()` outside the toolkit runs normally); both the 7.1 path and the pre-7.1 path.
- Integration (real 7.1 core, extend `tests/Integration/AbilitiesToolkitTest.php` or `AbilitiesTest.php`, which already registers a real "execute any ability" tool driven through POST /chat): a real meta-ability allowlisted, the model's call asks it to run a non-allowlisted ability → that ability's callback does not run and the tool result carries the refusal; the same through to `alpaca-bot/chat`.

**Docs.** Rewrite the AbilitiesToolkit class docblock paragraph that says an allowlisted meta-ability "reaches whatever those can reach", the matching Help tab text (`src/Admin/HelpTabs.php`), `Abilities\Register`'s docblock where it says the same, and README.md's non-changelog text. State exactly what is guarded and what is not (e.g. a plugin that calls another ability's callback directly without `execute()` is outside it).

### Task 2: #4541 — drop a toolkit that offers no tools before choosing the agent loop

**Problem.** A toolkit that is enabled but offers no tools (an MCP server whose client is unavailable or lists nothing approved; abilities enabled with nothing ticked) still makes `Chat\Pipeline::toolkitsFor()` return a non-empty set, so the turn runs through the agent loop offering the provider only `done`.

**Ruling T2-a (where).** In `Pipeline::toolkitsFor()`, not in `Toolkit\Registry::enabled()`: Registry is also asked by the `[alpacabot_agent]` shim and by abilities' permission checks, which must stay free of any listing (McpToolkit's docblock relies on that). Filter **after** the tools-capable decision (override / catalogue), so a model that cannot take tools still lists nothing. Keep the toolkit instances that survive — they are the ones `agentTurn()` receives, so McpToolkit's per-instance memo means the listing is not repeated.

**Measure first (the ticket asks).** Before changing code, write a test that counts `listTools()` calls on the MCP client for one turn in each case: (a) tool-capable model, MCP toolkit with approved tools; (b) tool-capable model, MCP toolkit that lists nothing; (c) model that cannot take tools. Record the counts before and after the change in your report. Expected: (a) 1 before and after; (b) 1 before and after; (c) 0 before and after. If the numbers differ, stop and report DONE_WITH_CONCERNS with the numbers.

**Tests.** A turn whose every enabled toolkit offers no tools takes the plain chat path (provider `stream()` called, no agent run, no `done` tool offered); a turn with one empty and one non-empty toolkit runs the agent loop with only the non-empty one; the counts above. Update `toolkitsFor()`'s docblock and any Pipeline/McpToolkit docblock that describes the old behaviour (e.g. text saying the agent loop runs with only `done`).

### Task 3: #4540 — WP-CLI MCP server write refuses a row the way REST does

**Problem.** `wp alpaca-bot settings toolkits.mcp_servers '<json>'` (`Cli\ChatCommand::settings()` → `Store::set()`) silently drops a row the schema cannot keep (bad/`http` URL, userinfo, bad header name, bad or colliding prefix) — and with it the server's header secret and `access.mcp` entry. REST `PUT /settings` (`Rest\SettingsController::update()`) refuses: 400 `alpaca_bot_mcp_row` naming each row, 400 `alpaca_bot_mcp_address` for an address refused by the egress check, nothing written, and an `X-Alpaca-Bot-Mcp-Cleared` header for servers whose header value a URL move cleared.

**Ruling T3-a.** One source of truth: move the REST checks (`droppedRows()` with its reasons, the `refusals()` address check with `forgetPassed()`, and `clearedByMove()`) into one place both REST and CLI call (e.g. a method on `Mcp\ServerSettings` returning either a refusal — code, message, rows — or the cleared ids). REST behaviour and its existing tests stay byte-identical. The CLI, on refusal, calls its `$fail` closure (WP_CLI::error → non-zero exit) with the same message REST answers (which names each row by URL or `row N`), and writes nothing. On success with cleared servers, it prints a warning line naming them (through a write/warn closure, testable). Wire the dependency through `Plugin.php` where the command is registered.

**Out of scope.** `wp option update alpaca_bot_settings …` (core's command, through the registered sanitize callback) — say so in the report; do not change it.

**Tests.** Unit tests on `ChatCommand::settings()` for each refusal kind (stored-server row made invalid; new row with a URL; colliding prefix; address refused) → fail called with a message naming the row, `Store` not written; a valid write still stores and echoes; a URL move with a kept header value prints the cleared warning. Existing REST tests stay green unchanged (run `tests/Unit/Rest/*Settings*` and `tests/Integration/SettingsRoutesTest.php` / `McpSettingsTest.php`).

### Task 4: #4539 — the provider API key does not follow a moved base URL

**Problem.** A write that changes `provider.base_url` keeps the stored `provider.api_key` when the key is posted as `Schema::MASK` — and also when the key is simply left out, since `Store::replace()` keeps an omitted key. A writer allowed to change the URL (Settings › Access can lower `settings.write` below administrator) can point it at their host and receive the key on the next provider call.

**Ruling T4-a (rule).** Same shape as 0.6 Task 25 / ruling R76 for MCP header values (`Mcp\ServerSettings::clearedByMove()`, `moved()`, `origin()`): when a write changes `provider.base_url`'s scheme, host or port against the stored value, the stored `provider.api_key` is cleared unless the same write carries a new key (a string that is neither `''` nor `Schema::MASK`). MASK, omission and a non-string all read as "keep", and "keep" does not survive a move. A path or query change is not a move. Enforce it in `Schema::sanitize()` so every writer (REST, settings page via the registered sanitize callback, CLI, `Store::replace()`) passes through it. Reuse one origin comparison for both MCP rows and the provider URL (extract it; do not copy it).

**Ruling T4-b (`Store::set()`).** `Store::set($key, $value)` currently passes the whole held array with one key changed, so the stored plaintext key arrives in the input as if the writer had typed it, and would survive a move. `set()` must write only `[$key => $value]` (`replace()` already keeps every key left out). Verify no caller depends on the old shape.

**Ruling T4-c (notice).** The writer is told: REST adds response header `X-Alpaca-Bot-Cleared: provider.api_key` (mirroring `X-Alpaca-Bot-Mcp-Cleared`); the settings page shows an admin notice after the save the way Task 25 does for MCP (find how the page reports `clearedByMove()` and mirror it); the CLI prints a warning line. The decision "will this write clear the key" is one function, used by the notices and by the sanitize rule.

**Tests.** Unit: host change + MASK → cleared; host change + omitted key → cleared; port change and scheme change → cleared; path/query-only change → kept; host change + new key → new key kept; no URL change + MASK → kept; `Store::set('provider.base_url', …)` to another host clears; REST header present only when cleared; CLI warning. Integration: PUT /settings moving the URL with the mask → stored key is '' and the header is set.

### Task 5: #4384 — `provider.api_key` out of the autoloaded option

**Problem.** `alpaca_bot_settings` is autoloaded and holds `provider.api_key` in plaintext, so it sits in `alloptions` on every request.

**Ruling T5-a (shape).** Lift the key into its own option, `alpaca_bot_provider_key`, written with autoload off — the shape 0.6 set for MCP header values (`Mcp\Secrets`, `Mcp\ServerSettings::beforeSave()`): the settings row carries `Schema::MASK` when a key is kept and `''` when none is, never the key. A `pre_update_option_alpaca_bot_settings` listener does the lifting: posted MASK keeps the held key, `''` deletes the option, any other string replaces it. The settings option itself stays autoloaded (it is read on every request; making it non-autoloaded would cost an uncached query per request). Task 4's rule must keep working on top of this: "cleared by a move" becomes `''` in the row and a deleted key option.

**Readers.** Everything that needs the real key resolves it through one function (row MASK → the key option; a plaintext value still in the row, from a site not yet migrated → that value): `Provider\Factory` (the only sender), `Rest\SettingsController` reveal (`?reveal=1`, still `manage_options` unconditionally), `wp alpaca-bot settings provider.api_key` by name, and the model-catalogue flush in `Plugin.php` (`update_option_alpaca_bot_settings` compares `provider.api_key`, which will now be MASK before and after a key change — the flush must still happen when the key changes). Grep every other `provider.api_key` / `Schema::SECRETS` reader and decide each.

**Ruling T5-b (upgrade).** A one-time migration moves a plaintext key from the row into `alpaca_bot_provider_key` (autoload off) and rewrites the row with MASK. Detection costs nothing: the row is already in `alloptions`; "pending" means the row's `provider.api_key` is a string other than `''` and MASK. Run it where `Migrate04` runs (`init` priority 20 in `Plugin::register()`, which covers admin, front end, REST, cron and WP-CLI) — either as a new small class or as a step of the existing migration class if that fits its docblock's contract; justify the choice. Idempotent: a second run changes nothing. A key still in the row before the migration runs is still read (the resolver above), so no request between upgrade and migration loses the key. `uninstall.php` deletes the new option; extend `UninstallTest`.

**Accept (from the ticket).** `wp option get alpaca_bot_settings --format=json` still returns the settings (key shown as MASK); the key is absent from that row; `SELECT autoload FROM wp_options WHERE option_name = 'alpaca_bot_provider_key'` is not an autoload value (`wp_autoload_values_to_autoload()`); the key still reaches the provider; reveal still asks `manage_options`; the migration is idempotent and covered by an integration test against a real options table (seed a 0.6.0-shaped row with a plaintext key, run, assert, run again, assert unchanged).

**Docs.** `Mcp\Secrets`' docblock says the provider key lives in the autoloaded option — correct it. Update `Settings\Store`, `Settings\Schema` (SECRETS paragraph), `Rest\SettingsController` and CLI docblocks that describe where the key is kept.

### Task 6: #4690 — the provider client does not pick cURL on a host that disables it

Added by the coordinator on 2026-09-29, after the plan was written.

**Problem.** On a host that lists `curl_init`/`curl_exec` in `disable_functions` (common on shared hosting), `Provider\Factory` builds its HTTP client through Symfony's `HttpClient::create()`. That checks only `extension_loaded('curl')`, which is still true there, so it picks `CurlHttpClient`. The first provider request then throws `Error: Call to undefined function …curl_init()`, and chat fatals. `web_fetch` already refuses cleanly on these hosts (#4484), so the plugin's two HTTP paths disagree about the same host.

**Ruling T6-a.** Choose the client explicitly. Use `CurlHttpClient` only when cURL is really callable: `curl_init` and `curl_exec` exist and neither is disabled. Otherwise use Symfony's `NativeHttpClient`, with the same options `create()` would have passed. One function decides "is cURL usable" for the whole plugin. If #4484's web_fetch work already has one, reuse it; do not write a second. Apply the same choice to the MCP egress client: `Mcp\Egress` defaults to `HttpClient::create()` (see its docblock on the pinned transport, which handles Curl and Native differently), and `Provider\WpAiClientProvider` or `BearerHttpClient` may build clients too. Grep for every `HttpClient::create` and `new CurlHttpClient` in `src/` and decide each. Behaviour where cURL is usable is unchanged.

**Tests.**
- Unit: the chooser answers Native when `curl_init` or `curl_exec` is disabled or missing, and Curl otherwise. Use whatever seam #4484 used to stand in for `disable_functions`.
- Integration: a `@group no-curl` test in the style of `tests/Integration/NoCurlTest.php`, run with `WP_NO_CURL=1 WPH_SITE=ab061srv bash bin/test-integration.sh -- --group no-curl --fail-on-skipped`. It proves that a provider call made through `Provider\Factory`'s real client succeeds or fails with a message, never with a fatal `Error`. Use a local stub endpoint or a refused address: the suite refuses unstubbed WP_Http, so pick a route the test controls. It also proves the MCP egress transport is Native there. The rest of the suite stays green in both modes.

**Docs.** Correct every docblock that says the client comes from `HttpClient::create()` (Egress, Factory), and verify each new claim.
