## Task 1: Kanboard #4691 — one synchronous snapshot of every per-turn input in `send()`

Since #4525, `resources/ts/boot.ts` `send()` captures `transcript` and `conversation` before its first await. It still reads `contextFrom(form)` (the post and screen chips; `mount.ts newChat()` replaces `.ab-composer__chips`) and `field('model').value` only when it builds `POST /chat`, which is after awaiting `/view/bubble`. A New chat in the drawer or sidebar in that window changes the chips of a turn that is still bound to the old conversation. A model change in that window changes the model.

Fix: take every per-turn input that goes into the ticket in one synchronous snapshot at the top of `send()`: conversation, context, model, the message text and images, and anything else `POST /chat` sends. Audit the whole of `send()`, and whatever it calls after an await, for other reads of mutable form state.

Test with the deferred-await harness from #4525 (`heldTurn()` with its `bubbles` gate in `tests/ts/chat.test.ts`):
- Remove a chip, send, and press the drawer's New chat while the bubbles are held. Assert that `chat().context` is the pre-switch context.
- Do the same for a model change.

## Task 2: Kanboard #4692 — a turn refused before sending must not restore its draft into another conversation's composer

When a turn is refused before it is sent (the never-ran path: a refused bubble or ticket, a rejected fetch, or a failed redeem before `sent = true`), `send()`'s `finally` calls `composer.ts restoreDraft()`. That sets `textarea.value = draft.text` unconditionally and puts back the image. After #4525's fix-wave commit 6ad3e1c, this is deliberate even after a switch, and a test covers it ("never-ran path after a switch: notice shown, draft restored"). The draft therefore lands in the composer that now shows another conversation, overwriting anything typed there.

Required behaviour, per the ticket:
- Restore the draft only when the composer still shows the conversation the turn was bound to (`shown()`), and never over non-empty input (text typed, or an image picked, since the send).
- Otherwise leave the user's input alone and say the message was not sent.

Decide how the unsent text stays recoverable. For example, the notice could quote or offer it, or the text could be restored when the composer is empty and the transcript is the same one. Prefer the smallest behaviour that loses no user text. If every option loses text in some case, pick the one with the least loss and document it.

Update the #4525 test that pins the old behaviour. Keep the existing composer e2e cases green ("a refused ticket gives the message and the image back", "a bubble render that fails gives the message and…"); they cover the same-conversation path.

## Task 3: Kanboard #4693 — `rememberConversation` dedups against what this tab last wrote

`resources/ts/mount.ts rememberConversation()` is shared by `drawer-start.ts` and `editor-start.ts`. It skips the `POST /view/drawer` write when the id equals the host element's `data-conversation`, which starts at the page-load value (the stored user meta at load time). With two tabs, tab A loads on 5 and tab B moves to 7, so the meta is 7. Tab A keeps chatting in 5, every announcement of 5 is deduped, and the next screen opens 7 even though the user's last activity was in 5.

Fix:
- Dedup against the last value *this tab* wrote. Before the tab's first write that value is "nothing", so the tab's first announcement writes.
- Record the value as written after the write.
- Decide and document the cross-tab rule. Recommended: last activity wins. Whichever tab last announced a conversation (a turn's start/done, a history switch, a New chat) owns the memory. Each tab writes at most once per change of what it shows, plus once for its first announcement.
- Check what announces on page load or mount. If a mere page load or drawer open would now write, say so, and decide whether that is acceptable. It likely is: one small POST per open.
- Keep `data-conversation` meaning what it means to its other readers. Grep them: the drawer mounts `/view/panel` from it.

Tests in `tests/ts` (drawer.test.ts, editor.test.ts): the two-tab scenario from above, as a unit test.

Docs: update the docblocks and `docs/api.md`'s `POST /view/drawer` row if it describes when the drawer writes.

It covers the Chat row's menu line (`Menu::capability`) and the listing of REST controllers through `alpaca_bot/rest/controllers`. `setInCodeEach()` (#4537) already logs a caught throwable under WP_DEBUG in the same format as `Access::overridden()`.

Tests: Pest, and the integration test pattern in `tests/Integration/SettingsPageTest.php` if the existing log assertions live there. Cover a throwing menu filter and a throwing `alpaca_bot/rest/controllers` filter, each logging one line.
