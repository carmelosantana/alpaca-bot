## Task 1: Kanboard #4525 — switching conversation mid-turn lets `done` restore the old id

**Priority of the set: a data-integrity bug.**

Symptom: while a turn is still streaming/finishing, switching conversation — the history select on the chat screen (htmx swap of `#ab-messages`), or "New chat" in the admin-wide drawer (`ab:new-chat` → `mount.ts newChat()` swaps a fresh transcript in) — is followed by the turn's `done` frame, whose handler `finish()` in `resources/ts/boot.ts` calls `setConversation(d.conversation_id)` with the *old* conversation's id. The transcript shows one conversation while the hidden `conversation_id` field (and so the next message) points at another; the drawer also remembers the wrong id via `ab:conversation`.

Hypothesis from the ticket: one guard in `boot()` — a turn remembers the conversation it started on, and a `done` for a turn whose conversation is no longer the open one does not move the field. Verify it covers every path: the `start` frame also calls `setConversation` (a brand-new chat's first turn starts on conversation 0 and learns its id from `start`, so "the conversation it started on" must be defined so that a new chat's first turn still records its id); `finish()` also swaps the bubble and triggers `ab:refresh` (the history select reload) — decide what should happen to those when the user has moved on (the bubble may no longer be in the document). Consider whether the guard is better keyed on "the transcript this bubble belongs to is still the one shown" than on id comparison. Choose the smallest correct design and justify it in the docblock.

Tests: a regression test in `tests/ts` (see `tests/ts/chat.test.ts` for how boot() is driven with a fake fetch/SSE stream) that reproduces the race — start a turn, switch conversation (simulate the htmx swap of `#ab-messages` with a different `data-conversation`, and separately the drawer-style new chat), then deliver `done` with the old id — and asserts the field (and `ab:conversation` events) stay on the newly opened conversation. Also keep a test that a normal turn (no switch), including a new chat's first turn from conversation 0, still records its id. Watch the regression test fail before the fix.

E2E: if feasible, add a Playwright case (tests/e2e/chat.spec.ts or drawer.spec.ts; the e2e provider mu-plugin `tests/e2e/mu-plugins/alpaca-bot-e2e-provider.php` fakes the model) that switches conversation mid-turn and asserts the next message lands in the newly opened conversation. If the provider cannot hold a turn open long enough to race deterministically, say so in the report with the reason rather than writing a flaky test; the controller will run e2e.

## Task 2: Kanboard #4526 — drawer's REST nonce goes stale before the first open

The admin-wide drawer's loader (`resources/ts/drawer.ts`) reads the REST nonce from page load (`window.alpacaBot?.nonce`), but the nonce refresh (`watchNonce()` in `resources/ts/nonce.ts`, on the heartbeat) is only called from `boot.ts`, which is in the chat bundle loaded on first open. A tab left open past the nonce's life with the drawer never opened fails that first open ("Reload the page and try again"), and `POST /view/drawer` saves fail silently.

Hypothesis: `drawer.ts` calls `watchNonce()` itself. Verify: where the drawer's nonce actually comes from before the chat bundle loads (`window.alpacaBot` vs `window.alpacaBotMount`, see `Admin\Drawer` and `mount.ts`), that the heartbeat script is actually a dependency of the drawer script on every screen it's enqueued on (check the PHP enqueue), that the server answers `alpaca_bot_nonce` for a heartbeat from those screens, and that the chat bundle's own `watchNonce` after boot does not conflict (double registration is idempotent or harmless). The nonce the drawer passes to `mountPanel` / `newChat` / `save()` and the one the booted chat uses must be the fresh one. Unit-test in `tests/ts` with a stub `window.jQuery` that fires `heartbeat-tick`, driving drawer's start logic (it may need to be made testable the way boot() was, without an import-time capture of globals — see `tests/ts/env.ts`).

## Task 3: Kanboard #4527 — editor sidebar reopens the remembered conversation, as the drawer does

The block-editor sidebar (`resources/ts/editor.ts`) always mounts `GET /view/panel` on a new chat. The drawer reopens the conversation stored through `POST /view/drawer` (user meta `alpaca_bot_drawer_conversation`).

Ruling (controller): the sidebar **shares the drawer's memory** (one user-meta value, not per post) — so the drawer, the sidebar and the chat screen agree on "the conversation you last had open", as the ticket's stated goal and the task request say. Concretely: the sidebar mounts `/view/panel` with the remembered conversation id; when the sidebar's chat announces a conversation (`ab:conversation`) or starts a New chat, it records it through `POST /view/drawer` (`conversation_id`) the way drawer.ts's `remember()` does — without touching the drawer's `open` flag. The post chip behaviour (auto-draft, post chip fetched after save) must keep working; check how `newChat` vs a remembered conversation interacts with the post chip and the `mount.ts postChip()` flow. Server side: find how the drawer receives the remembered id (data attribute printed by `Admin\Drawer`) and deliver the same value to the editor bundle (`Admin\Drawer::enqueueEditor()`), with PHP tests (Pest) as the repo does. Prefer sharing code with drawer.ts (e.g. move `remember`/`save` into mount.ts) over duplication.

Docs: the help tab (`src/Admin/HelpTabs.php`) and `docs/api.md` (around lines 655–670 and 1010–1022) currently say the sidebar opens / starts on a new chat; update both to say it reopens the conversation you last had open in the drawer or sidebar, and keep `POST /view/drawer`'s row accurate about who writes it. Grep for any other doc/docblock that says the sidebar starts on a new chat (including editor.ts's own docblock, and e2e specs) and fix it. Update `tests/e2e/editor.spec.ts` if it asserts a new chat on open.

## Task 4: Kanboard #4537 — Settings › Access "set in code" notes check every governed surface

`src/Admin/SettingsPage.php` `renderAccess()` tells an operator when a capability filter in code overrides a row. Two rows ask only one of the surfaces they govern:

- Chat row, API side: only `POST /chat`'s route filter (`alpaca_bot/capability/chat`). A site that filters only another chat route — `conversations`, `chat/stream`, `view/*`, `models`, `usage` — gets no note.
- Shortcode row: only the `alpacabot` tag, not `[alpacabot_agent]`.

Change: ask each governed route/tag and list every surface a filter changed. Find the authoritative list of chat routes and shortcode tags in code (the REST route registration and `Access` / `Shortcodes`) and derive the list from there rather than duplicating string literals, if the code offers a single source; otherwise add one. Each ask must pass the runtime's argument shape (the same arguments the filter receives at runtime) inside a try/catch (as `Access::overridden()` does — never let a throwing filter break the settings page). A filter with side effects will be called once per route; keep the number of calls to one per governed surface and document that in the docblock. Update the help tab text and docblocks that say which single route/tag is asked. Pest tests first: a filter on only one non-`chat` route yields a note naming that surface; a filter only on `alpacabot_agent` yields a note; a throwing filter does not break the page; no filter yields no note.
