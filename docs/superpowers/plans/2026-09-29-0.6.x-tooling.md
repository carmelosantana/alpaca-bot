Four tooling tickets on Kanboard project 17: #4469, #4485, #4484, #4554. Branch `fix/0.6.x-tooling`
from `develop`. No version bump, no `readme.txt` edit. Any new GitHub Action is pinned to a
commit SHA.

## Global Constraints

- No new Composer, npm or Action dependency unless vetted with `/powerup:supply-chain`.
- `composer check` and `pnpm check` stay green after every task.
- The `analyse` script's `--memory-limit` is not raised (#4469: raising it would hide contention).
- Comments and docblocks match the repo's style: they say why, and every figure they quote is one
  that was measured or is derived, never a count that will rot.

## Task 1: per-checkout PHPStan cache (#4469)

`phpstan.neon.dist` sets no `tmpDir`, so every worktree shares `sys_get_temp_dir()/phpstan` and a
worker OOMs reconciling another checkout's result cache. Set `parameters.tmpDir` to a directory
inside the checkout (PHPStan resolves relative paths against the config file's directory), for
example `.phpstan-cache`, and add it to `.gitignore`. Also gitignore a local `phpstan.neon`
override, mirroring the `phpcs.xml` precedent, since `phpstan.neon` takes precedence over
`phpstan.neon.dist` and is currently untracked-but-committable. Make sure `.distignore` keeps
the cache directory out of the zip (it holds absolute paths).

Acceptance: run `composer analyse` concurrently from two worktrees of this repo, repeatedly
(at least 5 concurrent pairs), all green, and record the command and output. Confirm
`git status` is clean after a run.

## Task 3: exercise web_fetch's refusal where WordPress would not use cURL (#4484)

Ruling: a CI step that runs the real integration suite on a PHP whose cURL functions are
disabled via `-d disable_functions=curl_init,curl_exec`. Requests' `Transport\Curl::test()`
checks `function_exists('curl_init') && function_exists('curl_exec')` first, so it answers false
through the real code path, Requests' own selector falls through to Fsockopen, and
`WebFetchToolkit::curlCarries()` must agree. This is the configuration shared hosts actually
ship (curl_exec in disable_functions). A test seam that forces `Curl::test()` false would only
re-test our closure, which the unit suite already does by injection.

- Add integration tests (their own `@group`, e.g. `no-curl`) asserting, with cURL disabled:
  `curlCarries(true)` and `curlCarries(false)` are false; Requests' `get_transport_class()`
  (reflection, as the existing test does) does not pick Curl; `web_fetch` executed with the
  toolkit enabled refuses with an error naming cURL and makes no request; the Site Health test
  reports `recommended` with the no-cURL label. Each test skips when cURL functions exist.
- `bin/test-integration.sh` gains a way to run with cURL disabled (e.g. `WP_NO_CURL=1` adds
  `-d disable_functions=curl_init,curl_exec` to the php invocation) in both modes, validated like
  the other env inputs.
- `.github/workflows/ci.yml`: on the latest leg only, a step running
  `WP_NO_CURL=1 ... bin/test-integration.sh --group no-curl --fail-on-skipped`.
- Update the comments in `tests/Unit/Toolkit/WebFetchToolkitTest.php` and
  `tests/Integration/ToolkitsTest.php` that say the branch is unreachable.

Acceptance: run the group locally on a disposable wp-harness site (`WPH_SITE=<own site>`), with
and without `WP_NO_CURL=1`, and show both outcomes.
