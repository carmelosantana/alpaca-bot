# WordPress 7.0 AI layer — what it is and how Alpaca Bot should integrate

Research for Kanboard #2941. Date: 2026-09-05. Primary sources only (make.wordpress.org,
developer.wordpress.org, wordpress.org, WordPress/* GitHub repos). Community sources are
labelled as such.

## TL;DR

1. WordPress 7.0 (released 2026-05-20) shipped three separate things: the **Abilities API**
   (actually 6.9), the **Connectors API** (`Settings → Connectors`, credential storage), and the
   **WP AI Client** (`wp_ai_client_prompt()` → `WP_AI_Client_Prompt_Builder`), with a vendored copy
   of `wordpress/php-ai-client` at `wp-includes/php-ai-client/`.
2. Core ships **zero AI providers**. Providers are plugins that call
   `AiClient::defaultRegistry()->registerProvider(...)`; a plugin can absolutely register
   Ollama/OpenAI-compatible/Anthropic itself, and a working Ollama provider plugin already exists.
3. The core client covers multi-turn chat (`with_history()`), structured output
   (`as_json_response($schema)`), images/multimodal, and **tool calling via Abilities**
   (`using_abilities()` + `WP_AI_Client_Ability_Function_Resolver`). **Streaming is not in the
   WP-level API** — it landed in php-ai-client for 7.1 but is explicitly "not naturally supported
   by WordPress".
4. wordpress.org has **no AI-specific plugin guideline**. What binds Alpaca Bot is the existing
   Guideline 6/7/8/10 stack: documented external service, explicit opt-in consent, no arbitrary
   code execution, no forced "powered by". The AI Guidelines handbook is about *contributing to
   WordPress*, not about shipping plugins.
5. Recommendation: **(b) — one provider behind an in-house `ProviderInterface` adapter.** Adopt
   Connectors + Abilities now (cheap, standards-aligned), treat WP AI Client as an *optional*
   provider, and keep the direct Ollama transport as the default because streaming and Alpaca
   Bot's PHP 8.1 / WP-version floor rule out making core the sole path.

## 1. What shipped in core 7.0 vs what is still a feature plugin

### Timeline and versions

| Thing | Status | Since |
|---|---|---|
| Abilities API (PHP) | **Core** | WordPress 6.9 |
| Client-side Abilities API (JS) | **Core** | WordPress 7.0 |
| Connectors API + `Settings → Connectors` | **Core** | WordPress 7.0 |
| WP AI Client (`wp_ai_client_prompt()`) | **Core** | WordPress 7.0 |
| `wordpress/php-ai-client` (Composer SDK) | Vendored into core; still standalone | v1.4.0 latest |
| `wordpress/wp-ai-client` (Composer/npm) | **Deprecated for 7.0+**, polyfill for < 7.0 | — |
| AI provider plugins (OpenAI / Anthropic / Google) | **Plugins**, not core | — |
| MCP Adapter (`WordPress/mcp-adapter`) | **Feature plugin** | — |
| `WordPress/ai` ("AI Experiments") | **Feature plugin** | — |
| Streaming, embeddings in php-ai-client | php-ai-client only, WP 7.1 cycle | — |

WordPress 7.0 "Armstrong" was released **May 20, 2026**
([release schedule](https://make.wordpress.org/core/2026/04/22/wordpress-7-0-release-party-updated-schedule/),
[Field Guide](https://make.wordpress.org/core/2026/05/14/wordpress-7-0-field-guide/)). WordPress 7.1
was in RC as of the [7.1 Field Guide](https://make.wordpress.org/core/2026/08/05/wordpress-7-1-field-guide/)
(published 2026-08-05).

### Namespaces and file locations

- WordPress wrapper: **`WP_AI_Client_Prompt_Builder`** (global namespace, WP naming conventions,
  snake_case methods, returns `WP_Error`). Source:
  `wp-includes/ai-client/class-wp-ai-client-prompt-builder.php`
  ([reference](https://developer.wordpress.org/reference/classes/wp_ai_client_prompt_builder/)).
- Sibling: `wp-includes/ai-client/class-wp-ai-client-ability-function-resolver.php`, plus
  `wp-includes/ai-client/adapters/` containing `class-wp-ai-client-cache.php`,
  `class-wp-ai-client-discovery-strategy.php`, `class-wp-ai-client-event-dispatcher.php`,
  `class-wp-ai-client-http-client.php`
  ([source tree](https://github.com/WordPress/wordpress-develop/tree/trunk/src/wp-includes/ai-client)).
- Vendored SDK: `wp-includes/php-ai-client/` containing `src/`, `third-party/`, `autoload.php`
  ([source tree](https://github.com/WordPress/wordpress-develop/tree/trunk/src/wp-includes/php-ai-client)).
  It is *not* a `composer.json` dependency of `wordpress-develop` — it is committed into `src/`.
- SDK namespace: **`WordPress\AiClient`** — `AiClient`, `PromptBuilder`, `EmbeddingBuilder`,
  `ProviderRegistry`, plus enums such as `WordPress\AiClient\Messages\Enums\ModalityEnum`,
  `WordPress\AiClient\Files\Enums\FileTypeEnum`, `WordPress\AiClient\Files\Enums\MediaOrientationEnum`
  ([repo](https://github.com/WordPress/php-ai-client),
  [dev note](https://make.wordpress.org/core/2026/03/24/introducing-the-ai-client-in-wordpress-7-0/)).
- Connectors: **`WP_Connector_Registry`** singleton, bootstrapped by `_wp_connectors_init()` on `init`
  ([dev note](https://make.wordpress.org/core/2026/03/18/introducing-the-connectors-api-in-wordpress-7-0/)).

### Explicitly out of scope for core

The merge proposal is unambiguous about the boundary:

> "This merge does not ship any AI providers or automatically enable AI calls. Without explicit
> configuration and explicit calling code, WordPress will not send prompts or data to any external
> service."

Core got the PHP API + prompt builder, provider abstraction, discoverability, HTTP integration,
credential UI, REST/JS endpoints and control filters. Bundled providers, end-user assistant UIs,
and product-level experiences were **excluded**
([merge proposal](https://make.wordpress.org/core/2026/02/03/proposal-for-merging-wp-ai-client-into-wordpress-7-0/)).

The `wordpress/wp-ai-client` package is now "deprecated in favor of the built-in AI client in
WordPress 7.0+"; on 7.0+ it disables its own PHP SDK infrastructure (HTTP wiring, event dispatcher,
cache, credentials screen) and keeps only the REST endpoints (`/wp-ai/v1/generate`,
`/wp-ai/v1/is-supported`), the JS client, and the `prompt_ai` / `list_ai_providers_models`
capability filters ([UPGRADE.md](https://github.com/WordPress/wp-ai-client/blob/trunk/UPGRADE.md)).

## 2. Providers, credentials, and whether a plugin can register its own

### Short answer

**Yes — a plugin can register any provider it wants, including Ollama.** There is no gate, no
approval list, and no core-managed-provider-only mode. Core registers *connector metadata* for
Anthropic/Google/OpenAI so the Connectors screen can offer install buttons, but the actual provider
implementations come from plugins.

### Provider registration (php-ai-client layer)

```php
add_action( 'init', function () {
    $registry = AiClient::defaultRegistry();
    $registry->registerProvider( OllamaProvider::class );
}, 5 );

add_action( 'init', function () {
    AiClient::defaultRegistry()->setProviderRequestAuthentication(
        'ollama',
        new ApiKeyRequestAuthentication( '' )
    );
}, 30 );
```

A provider extends `AbstractProvider` (or `AbstractApiProvider` for HTTP services) and implements
`createProviderMetadata()` → `ProviderMetadata`, `createModelMetadataDirectory()` →
`ModelMetadataDirectoryInterface`, `createProviderAvailability()` → `ProviderAvailabilityInterface`,
and `createModel()`. Models extend `AbstractOpenAiCompatibleTextGenerationModel` (for
OpenAI-compatible endpoints — which is what Ollama exposes) or `AbstractApiBasedModel` +
`TextGenerationModelInterface`, implementing `generateTextResult( array $prompt ): GenerativeAiResult`
([custom-provider guide, community](https://github.com/soderlind/ai-provider-for-azure-openai/blob/main/docs/how-to-add-ai-provider.md)).

Provider slugs must match `/^[a-z0-9_-]+$/`.

> **Gotcha worth flagging:** model metadata must declare `outputModalities` and *every* supported
> `inputModalities` combination, and every caller-settable option (temperature, etc.) becomes a
> matching requirement. Undeclared options cause **silent rejection** of the model during selection.

### Ollama already has a provider

Two exist in the wild (both community, not WordPress-official):

- [`Fueled/ai-provider-for-ollama`](https://github.com/Fueled/ai-provider-for-ollama) —
  `Fueled\AiProviderForOllama\Provider\OllamaProvider`, default base URL `http://localhost:11434`,
  `OLLAMA_HOST` env var takes precedence, `Settings → Ollama` screen, uses Ollama's
  OpenAI-compatible API. Requires PHP 7.4+, php-ai-client `^1.3` **or** WordPress 7.0+.
- [`jonathanbossenger/wp-ollama-model-provider`](https://github.com/jonathanbossenger/wp-ollama-model-provider)
  — same idea, by a WordPress core AI contributor.

So the "register Ollama with core" work is largely off-the-shelf.

### Connector registration and credential storage

Connectors are registered on the `wp_connectors_init` action — the **only** supported entry point;
touching the registry outside it triggers `_doing_it_wrong()`.

```php
array(
    'name'           => 'Anthropic',
    'description'    => 'Text generation with Claude.',
    'logo_url'       => 'https://example.com/anthropic-logo.svg',
    'type'           => 'ai_provider',
    'authentication' => array(
        'method'          => 'api_key',
        'credentials_url' => 'https://platform.claude.com/settings/keys',
        'setting_name'    => 'connectors_ai_anthropic_api_key',
    ),
    'plugin'         => array(
        'file' => 'ai-provider-for-anthropic/plugin.php',
    ),
)
```

Registry methods: `register( $id, $args )`, `unregister( $id )`, `is_registered( $id )`,
`get_registered( $id )`, `get_all_registered()`. Public readers available after `init`:
`wp_is_connector_registered()`, `wp_get_connector()`, `wp_get_connectors()`.

**Third-party providers get connector registration for free.** During `_wp_connectors_init()` core
queries `AiClient::defaultRegistry()` and merges discovered provider metadata over the built-in
defaults, provider values winning. No extra registration code is required for an AI provider plugin.

**Credential resolution order** (three sources, highest first):

1. Environment variable (e.g. `ANTHROPIC_API_KEY`)
2. PHP constant — `define( 'ANTHROPIC_API_KEY', 'sk-...' );`
3. Database option — `connectors_{$provider_type}_{$provider_id}_api_key`
   (hyphens in the slug normalise to underscores, e.g. `azure-openai` →
   `connectors_ai_azure_openai_api_key`)

`env_var_name` and `constant_name` can be set in the `authentication` array to override the derived
names; `setting_name` overrides the option name.

**Two security facts that matter for Alpaca Bot's threat model:**

> "API keys stored in the database are not encrypted but are masked in the user interface."
> (Encryption is tracked in Trac #64789.)

> All plugins accessing a registered connector can retrieve stored credentials — there is **no
> per-plugin approval mechanism**.

Auth methods are `api_key` and `none`. Anything else needs a client-side JS connector registered via
`__experimentalRegisterConnector` from `@wordpress/connectors`.

All of the above from the
[Connectors API dev note](https://make.wordpress.org/core/2026/03/18/introducing-the-connectors-api-in-wordpress-7-0/).

## 3. The core client API surface

Entry point:

```php
$builder = wp_ai_client_prompt();                 // or wp_ai_client_prompt( 'Your prompt' )
```

Returns `WP_AI_Client_Prompt_Builder`. It is a thin wrapper: a `__call()` magic method converts
snake_case to camelCase and proxies to the underlying `PromptBuilder`, catching SDK exceptions and
converting them to `WP_Error`. Once an exception occurs the builder enters an error state and
subsequent calls silently return the stored error rather than throwing.

### Configuration methods

| Concern | Method |
|---|---|
| Prompt text | `with_text()` |
| File / image input | `with_file()` |
| **Conversation history (multi-turn chat)** | `with_history()` |
| System instruction | `using_system_instruction()` |
| Temperature | `using_temperature()` |
| Max tokens | `using_max_tokens()` |
| Top-p / top-k | `using_top_p()`, `using_top_k()` |
| Stop sequences | `using_stop_sequences()` |
| Model preference | `using_model_preference()` |
| **Abilities as tools** | `using_abilities()` |
| Function declarations (raw) | `using_function_declarations()` |
| Output modalities | `as_output_modalities()` |
| Output file type / orientation | `as_output_file_type()`, `as_output_media_orientation()` |
| **Structured output** | `as_json_response( ?array $schema )`, `as_output_schema()` |

### Generation methods

`generate_text()` (string\|WP_Error), `generate_texts( n )`, `generate_text_result()`,
`generate_image()`, `generate_images( n )`, `generate_image_result()`, `generate_result()`,
`generate_speech_result()`, `convert_text_to_speech_result()`, `generate_video_result()`.

Result object is `GenerativeAiResult`: `toMessage()`, `toTexts()`, `toImageFiles()`,
`getTokenUsage()`, `getProviderMetadata()`, `getModelMetadata()`. It is REST-serialisable via
`rest_ensure_response()`.

### Capability probing (no API call)

`is_supported_for_text_generation()`, `is_supported_for_image_generation()`,
`is_supported_for_text_to_speech_conversion()`, `is_supported_for_speech_generation()`,
`is_supported_for_video_generation()`.

### Chat

Multi-turn is `with_history( Message... )` using `UserMessage` / `ModelMessage` DTOs wrapping
`MessagePart` arrays. There is no dedicated "chat session" object — you own the history array.

### Structured output

```php
$schema = array(
    'type'  => 'array',
    'items' => array(
        'type'       => 'object',
        'properties' => array(
            'plugin_name' => array( 'type' => 'string' ),
            'category'    => array( 'type' => 'string' ),
        ),
        'required' => array( 'plugin_name', 'category' ),
    ),
);

$json = wp_ai_client_prompt( 'List 5 popular WordPress plugins with their primary category.' )
    ->as_json_response( $schema )
    ->generate_text();
```

### Tool calling — via Abilities

This is the part the 7.0 dev note under-documents but the class reference confirms.
`using_abilities( ...$abilities )` accepts `WP_Ability` objects **or** ability-name strings and
"registers WordPress abilities as function declarations for AI models"
([class reference](https://developer.wordpress.org/reference/classes/wp_ai_client_prompt_builder/)).
Ability names are mangled into function names with a `wpab__` prefix and `/` → `__`
(`my-plugin/search-posts` → `wpab__my-plugin__search-posts`).

The loop is manual and uses `WP_AI_Client_Ability_Function_Resolver`:

1. Build the prompt with `using_abilities()` (+ a system instruction about tool use).
2. Generate.
3. `WP_AI_Client_Ability_Function_Resolver::has_ability_calls( $result )`.
4. `execute_abilities()` to run them — 7.1 tightened this to check `is_ability_call()` per call
   before executing, with regression coverage for mixed ability/non-ability calls
   (Trac #65504, [7.1 Field Guide](https://make.wordpress.org/core/2026/08/05/wordpress-7-1-field-guide/)).
5. Append the function-response message to history and regenerate.

Underlying SDK DTOs: `FunctionDeclaration`, `FunctionCall`, `FunctionResponse` (php-ai-client 1.3.1
fixed their JSON schemas).

### Images / multimodal

```php
use WordPress\AiClient\Messages\Enums\ModalityEnum;

$result = wp_ai_client_prompt( 'Create a recipe and include photos.' )
    ->as_output_modalities( ModalityEnum::text(), ModalityEnum::image() )
    ->generate_result();

foreach ( $result->toMessage()->getParts() as $part ) {
    if ( $part->isText() ) {
        echo wp_kses_post( $part->getText() );
    } elseif ( $part->isFile() && $part->getFile()->isImage() ) {
        echo '<img src="' . esc_url( $part->getFile()->getDataUri() ) . '">';
    }
}
```

Modalities: TEXT, DOCUMENT, IMAGE, AUDIO, VIDEO. **Image input should be a base64 data URI** — the
core tutorial notes "sending a URL works on some providers and fails on others"
([Developer Blog tutorial](https://developer.wordpress.org/news/2026/07/build-your-first-ai-powered-wordpress-plugin/)).

### Streaming — NOT available at the WordPress level

The 7.0 dev note does not mention streaming at all. For 7.1 the AI team wrote that they are
"introducing streaming to the PHP AI Client", explicitly framed as:

> available within WP 7.1, but **not as something naturally supported by WordPress** … allowing
> developers and hosts to build proper support for future releases.

The motivation given is the 30-second server timeout vs multi-minute generations
([What's coming to the AI Client in WP 7.1](https://make.wordpress.org/ai/2026/06/19/whats-coming-to-the-ai-client-in-wp-7-1/)).
7.1 also adds **embeddings** to the AI Client (`EmbeddingBuilder`; php-ai-client 1.4.0 added the
embedding generation APIs), leaning on MySQL/MariaDB native vector storage.

**This is the single most important finding for Alpaca Bot.** A chatbot UI without token streaming
is a materially worse product, and core will not give you streaming through
`wp_ai_client_prompt()` in the 7.x timeframe.

### Control filters

```php
add_filter(
    'wp_ai_client_prevent_prompt',
    function ( bool $prevent, WP_AI_Client_Prompt_Builder $builder ): bool {
        if ( ! current_user_can( 'manage_options' ) ) {
            return true;
        }
        return $prevent;
    },
    10,
    2
);
```

When prevented: no API call, `is_supported_*()` returns false, `generate_*()` returns `WP_Error`.
Also `wp_ai_client_default_request_timeout` (return seconds).

The **client-side JS API is not in core** — it remains the `wp-ai-client` npm package hitting the
package's REST endpoints, gated by the `prompt_ai` capability (administrator by default). The dev
note's recommendation is to build your own per-feature REST endpoints with granular permission
checks rather than exposing the generic prompt endpoint.

## 4. Abilities API

### Registration (PHP, since 6.9)

```php
add_action( 'wp_abilities_api_categories_init', 'my_register_categories' );
add_action( 'wp_abilities_api_init', 'my_register_abilities' );

wp_register_ability_category(
    'wp-ai-workshop-demo',
    array(
        'label'       => __( 'WP AI Workshop Demo', 'wp-ai-workshop-demo' ),
        'description' => __( 'Abilities for the WP AI Workshop Demo.', 'wp-ai-workshop-demo' ),
    )
);
```

`wp_register_ability( $ability_name, $args )` where `$ability_name` is `namespace/ability-name`
(namespace = your plugin slug) and `$args` accepts:

```
'label'               => string
'description'         => string
'category'            => string   // exactly one, must be registered
'input_schema'        => array    // JSON Schema
'output_schema'       => array    // JSON Schema
'execute_callback'    => callable
'permission_callback' => callable
'meta'                => array( 'show_in_rest' => bool, 'mcp' => array( 'public' => bool ) )
```

Companion functions: `wp_unregister_ability()`, `wp_has_ability()`, `wp_get_ability()`,
`wp_get_abilities()`, and the `*_ability_category` equivalents. Hooks:
`wp_abilities_api_categories_init`, `wp_abilities_api_init`, `wp_before_execute_ability`,
`wp_after_execute_ability`; filters `wp_register_ability_args`,
`wp_register_ability_category_args`.

REST surface when `show_in_rest` is true, namespace `wp-abilities/v1`:
`GET /abilities`, `GET /abilities/{name}`, `POST /abilities/{name}/run`.

Direct execution: `wp_get_ability( 'ns/name' )->execute( array( ... ) )` returning result or
`WP_Error`. Abilities can call other abilities — that is the sanctioned composition pattern.

### 7.1 additions

- Filters `wp_ability_validate_input` / `wp_ability_validate_output` for validation beyond JSON
  Schema (return `true` or `WP_Error`).
- Action `wp_ability_invoked`, fired at the top of `WP_Ability::execute()` **before** input
  normalisation and permission checks — the right hook for audit/telemetry, since it also catches
  invalid-input and permission-denied invocations.
- Typed REST input coercion for `GET`/`DELETE` from `input_schema`.
- Unified public-exposure flag, `wp_get_abilities()` filtering, JSON Schema preparation layer with a
  **schema compiler for AI tool-calling compatibility**
  ([7.1 improvements](https://make.wordpress.org/core/2026/07/31/abilities-api-improvements-in-wordpress-7-1/),
  [JSON Schema prep](https://make.wordpress.org/core/2026/07/31/json-schema-preparation-for-client-compatibility-in-wordpress-7-1/)).

### Client-side abilities (7.0)

Two npm packages: `@wordpress/abilities` (pure state/registration/execution store, no server
dependency) and `@wordpress/core-abilities` (integration layer that auto-fetches server abilities
and categories over REST). JS API: `registerAbility()`, `registerAbilityCategory()`,
`executeAbility()`, `getAbility()`, `getAbilities()`, `unregisterAbility()`.

```javascript
const { ready } = await import( '@wordpress/core-abilities' );
await ready;
const { getAbility, executeAbility } = await import( '@wordpress/abilities' );
const result = await executeAbility( 'ability-name', { param: value } );
```

HTTP method for server abilities is derived from annotations: `GET` for readonly, `DELETE` for
destructive+idempotent, `POST` otherwise
([dev note](https://make.wordpress.org/core/2026/03/24/client-side-abilities-api-in-wordpress-7-0/)).

### Relationship to agents and tools

The mental model, stated by the AI team: abilities are the *registry of permission-checked actions*;
the AI Client is the *model transport*; the agent layer is the loop that projects abilities into the
model's tool format. One ability registration buys three consumers at once:

1. **In-process tool calling** — `using_abilities()` → `FunctionDeclaration`.
2. **REST** — `POST /wp-abilities/v1/abilities/{name}/run`.
3. **External MCP agents** — add `'mcp' => array( 'public' => true )` to `meta` and install the
   [MCP Adapter](https://github.com/WordPress/mcp-adapter) feature plugin, which exposes abilities
   as MCP tools/resources/prompts to Claude, VS Code, Cursor etc.
   ([Developer Blog](https://developer.wordpress.org/news/2026/02/from-abilities-to-ai-agents-introducing-the-wordpress-mcp-adapter/)).

`permission_callback` is the security boundary for all three. This is the highest-leverage,
lowest-risk piece of the whole WP 7 AI stack for a plugin like Alpaca Bot.

## 5. What wordpress.org expects of AI plugins

### There is no AI-specific plugin guideline

As of 2026-09-05, the
[Detailed Plugin Guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/)
contain **no section on artificial intelligence or machine learning**. What applies to Alpaca Bot is
the pre-existing external-service stack:

- **Guideline 6** — SaaS interfaces to third-party platforms are allowed provided the service offers
  substantive functionality and clear documentation, including a link to Terms of Use.
- **Guideline 7** — "Plugins may not contact external servers without *explicit* and authorized
  consent." Satisfied by opt-in, service registration, or a settings checkbox. Also: "Documentation
  on how any user data is collected, and used, should be included in the plugin's readme."
- **Guideline 8** — "Executing outside code within a plugin when not acting as a service is not
  allowed", but "externally loading code from documented services" is permitted if communication is
  secure.
- **Guideline 10** — all "Powered By" displays must be optional and default to off.

Separately, and repeatedly stated by the Plugins team: **WordPress does not accept new plugins that
allow arbitrary code insertion or execution, explicitly including AI tools that generate code
intended to be executed on the site**
([Plugin Developer FAQ](https://developer.wordpress.org/plugins/wordpress-org/plugin-developer-faq/)).
This is the guideline most likely to bite an agentic chatbot: an ability that lets the model run
arbitrary PHP/SQL, edit `functions.php`, or install code will get the plugin rejected. Ship narrowly
scoped abilities with tight `input_schema`s instead.

### The AI Guidelines handbook is about contributing, not shipping

[make.wordpress.org/ai/handbook/ai-guidelines/](https://make.wordpress.org/ai/handbook/ai-guidelines/)
(published Feb 2026) governs **contributions to the WordPress project itself** — not plugins in the
directory. Its five principles: responsibility (understand every line, run tests), transparency
("When AI meaningfully contributes to your work (beyond trivial reformatting), clearly mention
that"), GPLv2-compatible licensing including for tool output, licensing for non-code assets, and
quality over volume ("maintainers may close or reject contributions that appear to be 'AI slop'").

It is still worth complying with voluntarily: it's the direction of travel, an
[`ai-disclosure` tag](https://wordpress.org/plugins/tags/ai-disclosure/) already exists in the plugin
directory, and other teams (e.g. the
[Hosting Team AI Policy](https://make.wordpress.org/hosting/2026/08/26/hosting-team-ai-policy/)) have
adopted stricter mandatory-disclosure variants.

### Practical checklist for Alpaca Bot's readme.txt

1. Name every external service the plugin can contact (Ollama host, and any provider reachable via
   Connectors), with links to their ToS and privacy policy.
2. State that no data leaves the site until the user configures an endpoint — which is *already* the
   truthful position for a self-hosted Ollama plugin, and is a genuine differentiator worth stating
   plainly.
3. Opt-in by default. Never prompt on activation.
4. Document what is sent (prompt, history, post content) and what is stored (chat logs as CPTs).
5. Disclose AI-assisted development if meaningful; consider the `ai-disclosure` tag.
6. Audit every ability against "no arbitrary code execution".

## 6. Recommendation for Alpaca Bot

### Current state

`AlpacaBot\Api\Ollama` is a single hard-coded transport (`apiChat`, `apiGenerate`, `apiEmbedding`,
`apiTags`, `getModels`, `getApiUrl`), with an in-house agent layer at `AlpacaBot\Agents\AgentInterface`
(`init`, `job`, `schema`, `getArg`). `composer.json` requires PHP `^8.1`. There is no
`ProviderInterface` yet.

### Verdict: (b) — one provider behind an in-house `ProviderInterface` adapter

Not (a), not (c).

**Why not (a) "sole provider":**

- **No streaming.** Core will not stream through `wp_ai_client_prompt()` in the 7.x line, by explicit
  design statement. A chatbot that can't stream is a regression from what Alpaca Bot can do today by
  hitting Ollama directly.
- **WP version floor.** Making core the sole path means `Requires at least: 7.0`, released
  2026-05-20. That is a brutal cut of the installed base for a plugin whose whole pitch is
  self-hosting. The `wordpress/wp-ai-client` polyfill exists but is deprecated and only papers over
  the PHP API, not the missing capability.
- **Credential blast radius.** "All plugins accessing a registered connector can retrieve stored
  credentials without per-plugin approval." For a privacy-positioned plugin, making Connectors the
  *only* credential path is a story you'd rather not have to tell. It should be an option, not the
  only option.
- **Silent model rejection.** The metadata/`SupportedOption` matching rules mean a mis-declared
  option makes models vanish with no error. Owning your own transport keeps a debuggable escape
  hatch.

**Why not (c) "ignore":**

- Abilities + Connectors are free interop wins that cost very little. Registering abilities gets you
  MCP exposure, REST exposure, and core-agent discoverability for one registration each.
- Connectors is where users will *expect* to find API keys once they're on 7.0.
- Being AI-stack-native is going to matter for directory visibility and for the "works with core AI"
  expectation.
- The Ollama provider work is already done by third parties, so the reverse direction (Alpaca Bot's
  Ollama reachable by *other* plugins) is nearly free too.

**Why (b):** you keep streaming and the low WP floor, you gain OpenAI/Anthropic/Google/Azure for free
via the core provider ecosystem, and Connectors becomes an *additional* credential source rather than
a replacement. The core client becomes one row in your provider table.

### Phased plan

**Phase 1 — Abilities (do this first; works on 6.9+, no dependency on the AI client).**
Register each `AlpacaBot\Agents\*` agent as an ability under the `alpaca-bot/` namespace with real
`input_schema`/`output_schema` and a real `permission_callback`. This immediately makes Alpaca Bot's
agents callable by core, by REST, and by MCP clients — and it makes them callable as *tools* by any
provider, including your own Ollama transport, because you now have JSON Schema for each.

**Phase 2 — Connectors as a credential source.** On 7.0+, read
`connectors_ai_ollama_api_key` (or your own connector id) and register a connector for the Ollama
endpoint so it appears on `Settings → Connectors`. Keep the existing settings screen as the fallback
for < 7.0. Honour env var / constant precedence.

**Phase 3 — `WpAiClientProvider` as an optional provider.** Behind the adapter below, gated on
`function_exists( 'wp_ai_client_prompt' )`. Non-streaming, used for the providers Alpaca Bot doesn't
speak natively.

**Phase 4 — publish Ollama outward (optional).** Either depend on / recommend
`Fueled/ai-provider-for-ollama`, or register your own `OllamaProvider` with
`AiClient::defaultRegistry()` so other plugins' AI features route through the user's local Ollama.
Prefer recommending the existing plugin over duplicating it.

### Minimal adapter sketch

No implementation — names and signatures only.

```php
namespace AlpacaBot\Providers;

enum Capability {
    case Chat;
    case Streaming;
    case Tools;
    case StructuredOutput;
    case Vision;
    case ImageGeneration;
    case Embedding;
}

interface ProviderInterface
{
    public function slug(): string;
    public function label(): string;
    public function isAvailable(): bool;
    public function supports(Capability $capability): bool;

    /** @param Message[] $messages @return Response|\WP_Error */
    public function chat(array $messages, RequestOptions $options): Response|\WP_Error;

    /** @return iterable<Chunk>|\WP_Error — providers without Capability::Streaming may throw */
    public function stream(array $messages, RequestOptions $options): iterable|\WP_Error;

    /** @return string[] */
    public function models(): array;

    /** @return float[]|\WP_Error */
    public function embed(string $text, RequestOptions $options): array|\WP_Error;
}
```

Supporting value objects (all plain PHP 8.1, no WP dependency):

- `AlpacaBot\Providers\Message` — `role` (`Role` enum: System/User/Assistant/Tool), `content`,
  `toolCalls`, `toolCallId`, `images`
- `AlpacaBot\Providers\RequestOptions` — `model`, `temperature`, `maxTokens`, `topP`, `topK`,
  `stopSequences`, `systemInstruction`, `jsonSchema`, `abilities` (string[] of ability names)
- `AlpacaBot\Providers\Response` — `text`, `toolCalls`, `tokenUsage`, `raw`
- `AlpacaBot\Providers\ToolCall` / `ToolResult`
- `AlpacaBot\Providers\Chunk` — `delta`, `done`

Implementations:

```php
namespace AlpacaBot\Providers;

/** Wraps the existing AlpacaBot\Api\Ollama. Default. Full streaming + tools. */
final class OllamaProvider implements ProviderInterface { /* … */ }

/** Wraps wp_ai_client_prompt(). Only registered when the function exists. */
final class WpAiClientProvider implements ProviderInterface
{
    // supports(): Chat, Tools, StructuredOutput, Vision, ImageGeneration => true
    //             Streaming => false   <-- the whole reason this is not the sole provider
    //
    // chat():   wp_ai_client_prompt()
    //             ->with_history( ...$this->toWpMessages( $messages ) )
    //             ->using_system_instruction( … )
    //             ->using_abilities( ...$options->abilities )
    //             ->using_model_preference( … )
    //             ->generate_text_result();
    //           then map GenerativeAiResult -> Response, and
    //           WP_AI_Client_Ability_Function_Resolver::has_ability_calls() -> Response::$toolCalls
    //
    // stream(): throw UnsupportedCapabilityException
    //
    // models(): AiClient::defaultRegistry() model metadata, or the is_supported_* probes
}
```

Registry and glue:

```php
namespace AlpacaBot\Providers;

final class ProviderRegistry
{
    public function register(ProviderInterface $provider): void;
    public function get(string $slug): ?ProviderInterface;

    /** @return ProviderInterface[] */
    public function all(): array;

    /** @return ProviderInterface[] filtered by capability */
    public function supporting(Capability $capability): array;

    public function default(): ProviderInterface;   // user setting, falls back to Ollama
}

namespace AlpacaBot\Compat;

final class WordPressAi
{
    public static function hasClient(): bool;      // function_exists( 'wp_ai_client_prompt' )
    public static function hasAbilities(): bool;   // function_exists( 'wp_register_ability' )
    public static function hasConnectors(): bool;  // function_exists( 'wp_get_connector' )
}

namespace AlpacaBot\Abilities;

final class Register
{
    public static function init(): void;                    // hooks wp_abilities_api_*_init
    public static function fromAgent(AgentInterface $agent): array;  // -> wp_register_ability() args
}
```

The key structural point: `RequestOptions::$abilities` is a list of **ability names**, so the same
tool set flows to `using_abilities()` on the WP path and to your own function-declaration builder on
the Ollama path. One registration, both providers.

### Risks and watch items

- **Streaming in 7.2+.** If core ever exposes streaming through the WP-level API, revisit (a). Track
  the AI team's roadmap posts.
- **Connector credential sharing.** Document it in the readme; don't store an Ollama bearer token
  there if it grants anything beyond inference.
- **Ability composition ≠ agent loop.** Core gives you `using_abilities()` + `has_ability_calls()` +
  `execute_abilities()`, not a managed agent runtime. Your existing `Agents` layer still owns the
  loop, retries, and budgets.
- **`show_in_rest` / `mcp.public` are exposure decisions.** Default them off for anything mutating.
- **PHP floor.** php-ai-client targets PHP 7.4+; Alpaca Bot is 8.1+. No conflict, but don't inherit
  7.4-era idioms into the adapter.
