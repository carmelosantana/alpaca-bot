# Small cores, shareable files, gates that fail closed

The four leading coding-agent harnesses (OpenAI Codex CLI, Claude Code, pi and opencode) have converged on the same shape, and most of it transfers to Alpaca Bot. They run one agent engine behind many clients. Extensions are declarative files, mostly Markdown with frontmatter, that load lazily under a token budget, and code runs only at named hook seams that can deny or rewrite a tool call. Repo- or add-on-supplied config stays inert until a human trusts it. Safety comes from isolation plus a small number of rule-based gates, not from prompting on every call. Their growth came less from the binaries than from shareable content formats (Anthropic's `skills` repo has more stars than Claude Code itself) and from zero-marginal-cost sign-in. WordPress has already built most of the tool layer an Alpaca Bot harness needs. Since 6.9 the Abilities API gives namespaced, schema-typed, permission-checked tools. Since 7.1 it adds an execution-lifecycle filter pipeline (pre-execute short-circuit, permission override, result filtering, an "invoked" action) that is the natural home for approvals and receipts. The MCP Adapter turns abilities into MCP tools. Alpaca Bot's floor is WordPress 6.9, though, so the 7.1 filters need a fallback path. Live code editing is the one area where the harness analogies break down. WordPress has no OS sandbox, arbitrary PHP write is remote code execution, and the closest competitor (AI Engine) has shipped six authorization and file-write CVEs since 2024. The defensible design is a staged, diff-and-approve pipeline: preview in Playground, check with a loopback, promote atomically, refuse when the check fails, and keep it off any conversation that has read untrusted content. **Staleness:** opencode 2.0 (October 2026) rewrote its plugin and permission API, Codex retired several approval modes and moved its docs twice in 2026, and pi reversed its "no MCP" stance in September 2026. Sources older than those dates describe products that no longer exist in that form.

## Four harnesses, one architecture: files in, engine in the middle, clients outside

### Extension points are declarative files, namespaced and lazily loaded

Claude Code is the clearest example. Skills, commands, subagents, output styles and rules are Markdown with YAML frontmatter. Hooks config, `.mcp.json`, `plugin.json` and `marketplace.json` are JSON. **Code runs only at defined edges**: hook commands, MCP and LSP servers, monitors and `bin/` executables ([Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)). A plugin is a directory that bundles those files, and every component is namespaced under the plugin name (`deploy-tools:reviewer`). Paths that escape the plugin root are rejected, names that impersonate Anthropic fail `claude plugin validate`, and typed `userConfig` options are prompted for on enable, with sensitive values sent to the OS keychain ([same](https://code.claude.com/docs/en/plugins-reference)). A marketplace is just a `marketplace.json` catalog with git, npm, archive or monorepo-subdirectory sources, which can be pinned to a ref or sha ([Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)). Codex has the same layering: AGENTS.md instructions, `.agents/skills/`, `[mcp_servers]`, `hooks.json`, plugins that bundle skills and MCP connections, presets, and layered `config.toml` ([Build skills](https://learn.chatgpt.com/docs/build-skills); [Hooks](https://learn.chatgpt.com/docs/hooks)). opencode 2.0 loads plugins from npm, git or local paths, and reads Markdown agents, file-based commands and skills directories ([Plugins](https://opencode.ai/docs/plugins/); [Agents](https://opencode.ai/docs/agents/)).

The skill format is now effectively shared. Claude Code, Codex and pi all read a `SKILL.md` directory under the Agent Skills open standard ([Skills](https://code.claude.com/docs/en/skills); [pi docs/skills.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)). All three use **progressive disclosure**: only the name and description sit in context, the body loads when the skill is invoked, and bundled scripts run without being loaded. Codex caps the skill index at **2% of the context window** ([Build skills](https://learn.chatgpt.com/docs/build-skills)). Claude Code truncates each listing entry at **1,536 characters** ([Skills](https://code.claude.com/docs/en/skills)). Instructions follow the same convergence. AGENTS.md, now stewarded under the Linux Foundation and claimed by "over 60k open-source projects", resolves by the rule "nearest file wins, explicit prompt overrides all" ([agents.md](https://agents.md/)). Codex stops concatenating at **32 KiB** ([AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)), and Claude Code reads AGENTS.md when no CLAUDE.md exists ([Memory](https://code.claude.com/docs/en/memory)). Anthropic's 2025 skills post warns that malicious skills can exfiltrate data and should be audited ([Anthropic Engineering, Oct 2025](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).

pi takes a deliberately different route. Extensions are in-process TypeScript factories that receive `pi: ExtensionAPI` and can register tools, commands, providers, MCP servers and TUI components. They subscribe to roughly 40 lifecycle events, and `tool_call` can return `{block, reason}` ([docs/extensions.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)). Two of pi's details carry over well. First, a tool returns `{content, details}`: content goes to the model, and details go to the UI and state. Second, extension state is rebuilt from the active session branch, which keeps it consistent when the user forks or rewinds ([same](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)). The docs open with "Pi can create extensions. Ask it to build one", and Ronacher describes a write, `/reload`, test loop in which the agent extends itself ([Ronacher, Jan 2026](https://lucumr.pocoo.org/2026/1/31/pi/)). Even pi's later concessions ship as removable built-in extensions (`-builtin:mcp`), not as core changes ([docs/settings.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/settings.md)).

### Hooks are the enforcement seam, and they all default to failing open

Hooks have converged as well. Claude Code has **33 events** and five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`). Its exit-code contract is: 0 means OK and stdout is parsed as JSON, 2 means block with stderr as the reason, and anything else is a non-blocking warning. Exit 1 does *not* block ([Hooks reference](https://code.claude.com/docs/en/hooks)). `PreToolUse` can return `allow|deny|ask|defer`, rewrite input through `updatedInput`, or inject up to 10,000 characters of `additionalContext`. An `allow` cannot override another hook's block ([same](https://code.claude.com/docs/en/hooks)). Codex mirrors this almost exactly. `PreToolUse` can deny or rewrite, `PermissionRequest` can answer an approval, exit 2 blocks, and a non-managed hook must be reviewed through `/hooks` before it runs ([Hooks](https://learn.chatgpt.com/docs/hooks)). opencode 2.0 replaced its flat V1 hook map (`tool.execute.before`, `permission.ask`) with per-domain APIs such as `ctx.tool.hook("execute.before")` and `ctx.permission.hook("evaluate")`, and broke every V1 plugin in the process ([Migrate V1](https://opencode.ai/docs/build/plugins/migrate-v1/); [AlternativeTo](https://alternativeto.net/news/2026/10/opencode-2-0-officially-launches-with-background-agents-code-mode-and-a-rebuilt-api/)).

The shared weakness is the default. **Hooks fail open**: a timeout or crash lets the tool run, in both Claude Code (until `onFailure: "block"` in v2.1.295+) and Codex ([Hooks reference](https://code.claude.com/docs/en/hooks); [Codex Hooks](https://learn.chatgpt.com/docs/hooks)). Claude Code's own docs call its hook `if` filter "not a security boundary". For a WordPress port, a guard filter that throws should deny, not allow.

### MCP is accepted only once its schemas stop sitting in context

Every harness now speaks MCP. The surviving design question is token cost. pi originally refused MCP because Playwright MCP alone costs about 13.7k tokens of schema per session ([Zechner, Nov 2025](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). It reversed in **0.99.0 (2026-09-29)**, and made MCP tools **undeclared by default** (`codemode` exposure): the model writes JavaScript that calls `tools.<name>()` in a QuickJS sandbox, finds tools through BM25 `searchTools()`, and caps listed declarations at 3,000 tokens ([CHANGELOG 0.99.0](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md); [docs/codemode.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/codemode.md)). Claude Code's tool search defers definitions by default and loads only tool names upfront ([MCP](https://code.claude.com/docs/en/mcp)). opencode 2.0 shipped a similar "Code Mode" ([AlternativeTo](https://alternativeto.net/news/2026/10/opencode-2-0-officially-launches-with-background-agents-code-mode-and-a-rebuilt-api/)). Codex adds governance per tool: `enabled_tools`/`disabled_tools`, a default approval mode, and per-tool `approval_mode` and `output_token_limit`. A tool that advertises a destructive annotation always prompts ([MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli); [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)). The WordPress MCP Adapter's default server takes the same economical approach. It exposes three meta-tools (discover, get-info, execute) rather than listing every public ability ([mcp-adapter README](https://raw.githubusercontent.com/WordPress/mcp-adapter/trunk/README.md)).

### Context is a budget with explicit re-injection rules

Claude Code is the most explicit about context. CLAUDE.md should stay under 200 lines. Subdirectory CLAUDE.md files and `paths:`-scoped rules load only when a matching file is touched, and only the first 200 lines or 25 KB of auto-memory load ([Memory](https://code.claude.com/docs/en/memory)). After compaction it **re-injects** a defined set: the system prompt, the root CLAUDE.md, memory, skill descriptions, the plan, git status, up to five recent files at 5K tokens each, and invoked skill bodies capped at 25K. It explicitly lets hook-added context and path-scoped rules lapse ([Context window](https://code.claude.com/docs/en/context-window)). Oversized output spills to files: MCP output defaults to a 25,000-token cap, and text over 50,000 characters is written to disk ([MCP](https://code.claude.com/docs/en/mcp)). In the documented example, a subagent read 9,890 tokens and returned a **420-token summary** ([Context window](https://code.claude.com/docs/en/context-window)).

The others add useful pieces. Codex's compaction prompt opens with "Create a handoff summary for another LLM that will resume the task" ([compact/prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md)). pi stores sessions as **append-only JSONL trees** with parent pointers, where only the active branch goes to the model and leaving a branch can summarize it into the next one ([docs/sessions.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)). opencode compacts with a hidden, cheap `compaction` agent that keeps a configurable token tail. On an agent's final allowed step it strips tools so the model must summarize ([Config](https://opencode.ai/docs/config/); [Agents](https://opencode.ai/docs/agents/)).

### One engine, many clients, with permissions as API objects

Each product puts one loop behind several surfaces. Codex serves its TUI, headless `codex exec` (JSONL events plus `--output-schema`), IDE and desktop app over an `app-server` JSON-RPC protocol ([Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)). Claude Code's `-p` mode offers `stream-json`, `--json-schema`, `--resume` and a recommended `--bare` that skips auto-discovered config, and the Agent SDK exposes the same loop with a `canUseTool` callback ([Headless](https://code.claude.com/docs/en/headless)). pi has TUI, print, JSON, RPC and an in-process SDK that OpenClaw embeds ([docs/how-pi-works.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/how-pi-works.md)). opencode 2.0 is the most server-shaped. It is a background service with an OpenAPI 3.1 API of 173 operations. Its session endpoints cover prompt, message and interrupt. It offers a **volatile** live event stream next to a durable, replayable per-session log, and it treats permissions as first-class objects: pending requests are listed and answered through a reply endpoint ([Server](https://opencode.ai/docs/server/)). That shape (session, prompt endpoint, event log, pending-approval objects) fits a PHP request lifecycle well. The agent loop must outlive any single admin page load, and SSE connections on shared hosting are fragile.

## Safety rests on isolation and rules, and prompts on every call are not a boundary

The harnesses split safety into two axes. Codex says so explicitly. The **sandbox mode** sets what a command can technically do (`read-only`, `workspace-write`, `danger-full-access`). The **approval policy** sets when a human is asked (`on-request`, `never`, or `granular` per category). Network is off by default ([Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)). Protected paths (`.git`, `.agents`, `.codex`) stay read-only even inside writable roots, so the agent cannot rewrite its own hooks or skills ([same](https://learn.chatgpt.com/docs/agent-approvals-security)). An optional **auto-review** agent can answer escalations in place of the human. It lets low and medium risk through, denies critical risk, and **fails closed** on parse errors or timeouts ([same](https://learn.chatgpt.com/docs/agent-approvals-security)). Claude Code layers six permission modes (Manual through `bypassPermissions`, which the docs restrict to containers or VMs) on top of **deny, then ask, then allow** rules where first match wins and an allow can never carve an exception out of a deny. A bare tool name in deny removes the tool from the model's context entirely ([Permissions](https://code.claude.com/docs/en/permissions)). Managed policy sits above CLI, project-local, project and user scopes, and list keys merge rather than override ([Settings](https://code.claude.com/docs/en/settings)). opencode uses `{action, resource-glob, effect}` rules with last match winning and **ask** when nothing matches. "Always" saves a scoped allow rule. A separate admin `policies` layer can only tighten ([Permissions](https://opencode.ai/docs/permissions/)). Its base policy allows almost everything, which is the wrong default for wp-admin.

**Trust gating** is the most portable idea of all. Codex ignores a project's `.codex/` config, hooks and rules until the project is trusted ([Config advanced](https://learn.chatgpt.com/docs/config-file/config-advanced)). Claude Code applies a committed settings file's deny rules immediately but holds back its allows until the folder is trusted ([Settings](https://code.claude.com/docs/en/settings)). pi gates every `.pi/` extension, MCP config and system-prompt override behind `project_trust` ([docs/security.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md)). The documented hole is headless mode. Claude Code's `-p` runs project hooks and `.mcp.json` servers "even in a folder you've never trusted" ([Headless](https://code.claude.com/docs/en/headless)). A WordPress cron or WP-CLI run of Alpaca Bot has the same exposure if add-on config is trusted implicitly.

pi is the steelman against all of this. Zechner calls permission prompts largely "security theater", because an agent that can read data, run code and reach the network cannot be made safe that way ([Zechner, Nov 2025](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)). pi's current docs still say transcript review and trust prompts "do not create a security boundary" and recommend a container or VM ([docs/security.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md)). Anthropic's data agrees on the mechanism: OS sandboxing cut permission prompts by **84%** internally, because isolation, not more prompts, makes autonomy usable ([Anthropic Engineering, Oct 2025](https://www.anthropic.com/engineering/claude-code-sandboxing); dated 2025). WordPress has no such OS layer. Its stand-ins are capability checks, a dedicated low-capability user, revisions and snapshots, and Playground. pi's YOLO stance therefore does not transfer. Its *mechanism*, one blockable `tool_call` event plus a trust gate, does.

Undo is the other half of safety, and every harness's version leaks. Claude Code's checkpoints snapshot edits made by its own edit tools. They do **not** cover Bash edits, most subagent edits or external changes, and the docs call them "not a replacement for version control" ([Checkpointing](https://code.claude.com/docs/en/checkpointing)). opencode's undo depends on filesystem snapshots ([Config](https://opencode.ai/docs/config/)). In WordPress, post revisions already give checkpoint semantics. Options, custom tables and files written by an ability do not, and need explicit snapshots before a write tool runs.

The sandboxes themselves get escaped. Codex shipped CVE-2025-59532, where a model-chosen cwd became a writable root ([Vulners](https://vulners.com/search/tags/codex%20ide%20extension?skip=-20); aggregator). In August 2026 it shipped "Overpatch", an `apply_patch` escape, patched within about 8 days ([CSA research note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/09/CSA_research_note_openai_codex_sandbox_escapes_20260922-csa-styled.pdf)). Pillar Security's cross-vendor escapes led to the argument that guardrails "can't live inside the agent" ([DevOps.com](https://devops.com/codex-sandbox-escapes-show-why-agent-guardrails-cant-live-inside-the-agent/)). opencode's record is worse and, for Alpaca Bot, more instructive, because the holes were in its **control endpoints**. They include an unauthenticated `POST /session/{id}/shell` (CVE-2026-22812) ([PT Security](https://dbugs.ptsecurity.com/vulnerability/PT-2026-2315)), a `/global/upgrade` code injection ([Datadog Security Labs](https://securitylabs.datadoghq.com/articles/opencode-upgrade-remote-code-execution/)), and code execution at MCP sign-in from a malicious server, fixed with no CVE ([The Hacker News](https://thehackernews.com/2026/10/opencode-flaw-lets-malicious-mcp.html)).

## Growth followed free sign-in and shareable content, not features

Codex shows the cleanest distribution story. It is Apache-2.0, ships as one static binary through curl, npm, Homebrew and DotSlash, and defaults to **"Sign in with ChatGPT"**, so existing subscribers pay nothing extra ([README](https://github.com/openai/codex/blob/main/README.md)). OpenAI's self-reported weekly users went from about **1M in early March 2026** ([Fortune](https://fortune.com/2026/03/04/openai-codex-growth-enterprise-ai-agents/)) to **5M by June 2** ([Constellation Research](https://constellationr.com/insights/news/openai-touts-broadening-codex-usage-5-million-weekly-active-users)) and **past 8M** after mid-July ([The New Stack](https://thenewstack.io/gpt-5-6-codex-user-surge/)). Those counts cover every Codex surface, not just the CLI. The repo sits at 135,967 stars with about 170 releases in roughly 19 months ([GitHub API](https://api.github.com/repos/openai/codex)).

Claude Code's numbers point to the content format as the lever. `anthropics/claude-code` has 156,412 stars, but **`anthropics/skills` has 197,926** ([GitHub](https://github.com/anthropics/claude-code); [anthropics/skills](https://github.com/anthropics/skills)). The official marketplace lists **317 plugins** ([marketplace.json](https://github.com/anthropics/claude-plugins-official/blob/main/.claude-plugin/marketplace.json)). pi shows the same effect from the minimalist side. It went from a personal tool in November 2025 to 123,033 stars, **26.8M npm downloads a month** (including OpenClaw and CI installs, so this is not a user count) and about **14,069 npm packages tagged `pi-package`** ([GitHub API](https://github.com/earendil-works/pi); [npm downloads API](https://api.npmjs.org/downloads/point/last-month/@earendil-works/pi-coding-agent); [npm search](https://registry.npmjs.org/-/v1/search?text=keywords:pi-package&size=1)). Much of that is long-tail. A long-time user on HN called most pi plugins personal "vibe-coded" projects (low confidence, read via a mirror; [hn.nuxt.dev](https://hn.nuxt.dev/item/48847407)), and pi responded by bundling first-party built-in extensions. opencode reached **228.2k stars** on provider neutrality: "200+ providers" via models.dev, with auto-discovery of Ollama at `127.0.0.1:11434` ([GitHub](https://github.com/anomalyco/opencode); [Providers](https://opencode.ai/docs/providers/)).

Their failures are just as instructive. Anthropic's April 2026 postmortem traced two months of degraded quality to **harness changes, not the model**: a lowered default effort, a caching bug that dropped prior reasoning every turn, and a verbosity prompt that cost 3% on evals. The fixes were per-model evals for every system-prompt change and staged rollouts ([Anthropic postmortem](https://www.anthropic.com/engineering/april-23-postmortem)). Codex's config churn broke real setups. `approval_policy = "untrusted"` now "can prevent either client from starting", `--full-auto` was removed, and `[profiles.*]` stopped being read in 0.134.0 ([Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security); [Config advanced](https://learn.chatgpt.com/docs/config-file/config-advanced)). opencode 2.0 broke every V1 plugin, and ecosystem plugins such as oh-my-opencode had to cut 2.0 releases ([newreleases](https://newreleases.io/project/github/code-yeongyu/oh-my-opencode/release/v2.0.0)). For a WordPress plugin, whose users auto-update and rarely read changelogs, the lesson is to deprecate with `apply_filters_deprecated` and keep aliases for a release, as the canonical AI plugin did when renaming abilities in 1.4 and removing them in 1.5 ([AI release tag](https://make.wordpress.org/ai/tag/ai-release/)), rather than refusing to boot.

## WordPress already ships the tool layer, but the best hooks need 7.1

### Abilities API: the tool contract (6.9) and the guardrail pipeline (7.1)

`wp_register_ability( $name, $args )` takes a namespaced name, `label`, `description`, `category`, `execute_callback`, `permission_callback`, JSON Schema `input_schema`/`output_schema`, and `meta.annotations` (`readonly`, `destructive`, `idempotent`). The annotations are documented as **hints**, not enforcement. Registration must happen on `wp_abilities_api_init`, and `wp_register_ability_args` can rewrite anyone's registration ([wp_register_ability reference](https://developer.wordpress.org/reference/functions/wp_register_ability/)). REST lives under `/wp-json/wp-abilities/v1`, and every route requires an authenticated user ([REST API endpoints](https://developer.wordpress.org/apis/abilities-api/rest-api/)). WordPress 7.0 added a JS client: `@wordpress/abilities` plus `@wordpress/core-abilities`, the store `core/abilities`, and `executeAbility()`. Client-side abilities run in the browser ([Client-side Abilities API in 7.0](https://make.wordpress.org/core/2026/03/24/client-side-abilities-api-in-wordpress-7-0/)).

WordPress 7.1 (released 2026-08-19) added what is effectively a harness hook pipeline ([7.1 schedule](https://make.wordpress.org/core/2026/07/03/wordpress-7-1-release-party-schedule/)). The order is: `wp_pre_execute_ability` (any return short-circuits; the dev note names **approval workflows**, caching, rate limiting and mocks as intended uses), `wp_ability_normalize_input`, `wp_ability_permission_result` (runs after `permission_callback`, applies to REST and WP-CLI, and can override a denial), `wp_before_execute_ability`, the callback, `wp_ability_execute_result` (redact or enrich, still schema-checked), then `wp_after_execute_ability` ([Lifecycle filters in 7.1](https://make.wordpress.org/core/2026/07/29/new-execution-lifecycle-filters-for-the-abilities-api-in-wordpress-7-1/)). A companion note adds `wp_ability_invoked`, which fires at the very start of `execute()` for **every** call, including cached, short-circuited, **approval-pending** and failed ones. It also adds `wp_ability_validate_input`/`_output`, and confirms that REST-style `sanitize_callback`/`validate_callback` keywords are not executed ([Abilities API improvements in 7.1](https://make.wordpress.org/core/2026/07/31/abilities-api-improvements-in-wordpress-7-1/)).

That pipeline is the Claude Code `PreToolUse`/`PostToolUse` contract, implemented in core and applied to any agent, not only Alpaca Bot. A receipt becomes three joined records: `wp_ability_invoked` (attempt), `wp_ability_permission_result` (decision) and `wp_after_execute_ability` (outcome). Each carries the user, the application-password UUID or MCP session, the ability, its annotations and redacted I/O. Capability narrowing belongs in `wp_ability_permission_result`, as an intersection with a per-agent allow-list that only ever turns `true` into a `WP_Error` and never the reverse. Two cautions apply. First, Alpaca Bot declares `Requires at least: 6.9`, and **none of the 7.1 filters exist on 6.9 or 7.0**. Gating there has to happen inside Alpaca Bot's own dispatch layer, with the core filters adopted when `has_filter`-style feature detection shows they are present. Second, several ability details are contested or unconfirmed. Whether `meta.public` arrived in 6.9 or 7.1 is unclear: the reference documents it, but the 7.1 post calls it "new". The REST method mapping for destructive abilities differs between the REST docs (DELETE for destructive) and the 7.0 JS note (DELETE only for destructive *and* idempotent) ([REST API endpoints](https://developer.wordpress.org/apis/abilities-api/rest-api/); [7.0 JS note](https://make.wordpress.org/core/2026/03/24/client-side-abilities-api-in-wordpress-7-0/)). Check trac before setting a floor on either.

### AI Client, the AI plugin and the MCP Adapter

Core 7.0's `wp_ai_client_prompt()` builder adds model-preference fallback, JSON output, token usage on results and a site-wide veto filter, `wp_ai_client_prevent_prompt`. Core bundles no providers, and the official Anthropic, Google and OpenAI provider plugins register keys on Settings > Connectors ([AI Client in 7.0](https://make.wordpress.org/core/2026/03/24/introducing-the-ai-client-in-wordpress-7-0/)). Trac #64938 reports that the SDK's before/after-generate events do not fire in 7.0, and its fix status is unchecked ([Trac #64938](https://core.trac.wordpress.org/ticket/64938)). The canonical **AI plugin** (formerly AI Experiments) reached **1.5.0 on 2026-10-29**. It ships an "MCP Access" screen that installs the MCP Adapter and chooses which abilities agents see, a WebMCP experiment for the block editor, an embeddings table, a shared `log_ai_request()` AI Request Log, and a **Site Agent planned for 1.6.0** ([AI release tag](https://make.wordpress.org/ai/tag/ai-release/)). That Site Agent is the most direct first-party competitor Alpaca Bot will face. The **MCP Adapter** (v0.7.2 per README) maps abilities to MCP tools, resources or prompts. Abilities are private by default. Custom servers are created on `mcp_adapter_init` with an explicit ability list, and transport auth defaults to application passwords, since self-hosted sites have no core OAuth. The official guidance is a dedicated low-capability user and no `__return_true` on destructive abilities ([MCP Adapter intro](https://developer.wordpress.org/news/2026/02/from-abilities-to-ai-agents-introducing-the-wordpress-mcp-adapter/)). Elementor and Bluehost both vendor the adapter ([Elementor vendor copy](https://fastly.jsdelivr.net/wp/plugins/elementor/trunk/vendor/wordpress/mcp-adapter/README.md)), so several copies can load on one site. Alpaca Bot should detect an existing instance rather than ship a competing copy.

### Add-on plumbing and the competitive field

`Requires Plugins:` (6.5+) enforces only that a dependency is *present*. It has **no version constraints and no load-order guarantee**, and it accepts only wordpress.org slugs from wp.org-hosted plugins ([Plugin dependencies in 6.5](https://make.wordpress.org/core/2024/03/05/introducing-plugin-dependencies-in-wordpress-6-5/)). A companion can declare `Requires Plugins: alpaca-bot`, but must check an Alpaca API-version constant at runtime, the way Gravity Forms add-ons declare `$_min_gravityforms_version` ([GF Add-On Framework](https://docs.gravityforms.com/add-on-framework/); not re-verified). Core's own registries all share one shape: a singleton registry, a `wp_register_*` function, and a dedicated `*_init` action that calls `_doing_it_wrong` outside it ([wp_register_ability reference](https://developer.wordpress.org/reference/functions/wp_register_ability/)). Alpaca Bot's toolkit registry should copy that shape exactly.

The competitive field has holes in the right places. **AI Engine** offers its own MCP server and filter-based tool hooks (`mwai_functions_list` and others), documented mainly in support threads ([wordpress.org/plugins/ai-engine](https://wordpress.org/plugins/ai-engine/); [support thread](https://wordpress.org/support/?p=18978595)). **AI Services** is a provider registry that now overlaps core ([wordpress.org/plugins/ai-services](https://wordpress.org/plugins/ai-services/)). **WordPress.com's hosted MCP** gained write abilities on 2026-03-20 behind OAuth 2.1 and per-operation toggles ([TechCrunch](https://www.techcrunch.com/2026/03/20/wordpress-com-now-lets-ai-agents-write-and-publish-posts-and-more/)). **Novamira** gives external agents PHP execution and filesystem access and is positioned for dev and staging only ([WP Mayor](https://wpmayor.com/novamira-ai-wordpress-mcp-plugin/)). Separately, governance companions have already appeared on wp.org: AbiliZen (exposure toggles plus MCP logs), Activity Log for MCP (keyed on the `Mcp-Session-Id` header) and MCP Tracker ([AbiliZen](https://wordpress.org/plugins/abilizen-ai-abilities/); [Activity Log for MCP](https://wordpress.org/plugins/activity-log-for-mcp/); [MCP Tracker](https://wordpress.org/plugins/mcp-tracker/)). That demand is evidence for a companion ecosystem, and none of these products offers a documented, versioned toolkit contract. No source showed WP Activity Log or Stream natively logging ability or MCP calls as of November 2026.

## Live code editing is remote code execution, so build it as a fail-closed pipeline

### The frank risk picture

Arbitrary PHP write is full-site compromise, and the WordPress record shows the endpoint is where it fails. WP File Manager's bundled elFinder connector allowed **unauthenticated PHP upload (CVE-2020-25213, CVSS 9.8)**. It is in CISA's KEV catalog and was still being used to drop Kinsing malware months later ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2020-25213); [Unit 42](https://unit42.paloaltonetworks.com/cve-2020-25213/)). Advanced File Manager has repeated the pattern through 2026 ([Wordfence listing](https://www.wordfence.com/threat-intel/vulnerabilities/wordpress-plugins/file-manager-advanced)). AI Engine is the closest analogue to Alpaca Bot, and its record is a checklist of what not to ship:

| CVE | What went wrong |
| --- | --- |
| CVE-2024-6451 | Admin RCE through a log path that wrote `.php` ([Wordfence](https://www.wordfence.com/threat-intel/vulnerabilities/wordpress-plugins/ai-engine/ai-engine-250-authenticated-admin-remote-code-execution)) |
| CVE-2025-7847 | Subscriber+ arbitrary upload over REST ([Rapid7](https://www.rapid7.com/db/vulnerabilities/ai-engine-plugin-cve-2025-7847)) |
| CVE-2025-12844 | Subscriber+ PHAR deserialization ([Wordfence](https://www.wordfence.com/threat-intel/vulnerabilities/wordpress-plugins/ai-engine/ai-engine-318-authenticated-subscriber-php-object-injection-via-phar-deserialization)) |
| CVE-2025-5071 | Subscriber+ privilege escalation via MCP, CVSS 8.8 ([Wordfence](https://www.wordfence.com/blog/2025/06/100000-wordpress-sites-affected-by-privilege-escalation-via-mcp-in-ai-engine-wordpress-plugin/)) |
| CVE-2025-11749 | Unauthenticated bearer-token exposure on `/mcp/v1/`, CVSS 9.8 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-11749)) |
| CVE-2026-8719 | Any valid MCP OAuth token got MCP access without a capability check ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-8719)) |

None of these needed the model to misbehave. The model adds a further vector that has no documented incident yet but follows directly from the design: **prompt injection**. A retrieved post, comment or fetched page that says "add a helper to functions.php" becomes RCE in one paragraph if a code-write tool is reachable from that conversation. The code-write tool therefore has to be unreachable from any session that has ingested untrusted content, and every diff needs a human approval bound to a nonce and to a hash of the exact bytes. Some hosts settle the question in advance. WordPress VIP, Pantheon Test and Live, and WP Engine Autoscale all serve **read-only code** ([VIP](https://docs.wpvip.com/plugins/incompatibilities/); [Pantheon](https://docs.pantheon.io/plugins-known-issues); [WP Engine](https://developers.wpengine.com/docs/managed-hosting-platform/autoscale/compatibility/)). `DISALLOW_FILE_EDIT` and `DISALLOW_FILE_MODS` are site owners explicitly saying no ([Hardening](https://developer.wordpress.org/advanced-administration/security/hardening/); not re-verified). On all of these, the feature should degrade to proposing a diff, opening a PR or offering a ZIP download.

### Core's safety nets are useful but leak

`wp_edit_theme_plugin_file()` writes the file and then runs a loopback "scrape" of the admin page and the front end with a one-time key, restoring the previous bytes on a fatal. It runs only for **PHP files of an active plugin or theme**. It is broken by HTTP Basic auth (so a bad edit is not rolled back), by multisite loopback URLs and by security plugins. It also leaves a window in which the live file is broken ([reference](https://developer.wordpress.org/reference/functions/wp_edit_theme_plugin_file/); [Trac #42102](https://core.trac.wordpress.org/ticket/42102); [Trac #44514](https://core.trac.wordpress.org/ticket/44514)). Recovery mode catches fatals after the fact, pauses the extension per user through a cookie and emails a link at most hourly. It slipped from 5.1 because pausing a plugin could bypass its 2FA ([Recovery mode in 5.2](https://make.wordpress.org/core/2019/04/16/fatal-error-recovery-mode-in-5-2/); [fatal error protection](https://make.wordpress.org/core/2019/03/20/the-improved-fatal-error-protection/)). The 6.3 rollback covers failed manual updates only, not edits ([Rollback in 6.3](https://make.wordpress.org/core/2023/07/11/new-in-6-3-rollback-for-failed-manual-plugin-and-theme-updates/)). The right move is to reuse the idea, not the function: write to a staged copy, loopback-test the copy, promote with an atomic rename, `opcache_invalidate()` the changed files, keep the prior version for one-click revert, and **refuse to apply when the loopback cannot run**.

### Isolation options, ranked by how real they are

**WordPress Playground** is the only true isolation for previewing agent-written PHP, because the code runs as WASM PHP in the admin's browser tab, not on the host. `@wp-playground/client` can `writeFile` and `run` against an embedded iframe, and Blueprints can turn networking off ([npm @wp-playground/client](https://npmjs.com/package/@wp-playground/client); [Using Blueprints](https://developer.wordpress.org/playground/blueprints/using-blueprints/)). PHP 8.4 is selectable ([Playground 2026-07-22](https://make.wordpress.org/playground/2026/07/22/manage-wordpress-playground-sites-programmatically/)). The limits are real. It uses SQLite rather than MySQL (the team claims 99%+ plugin compatibility), has no pcntl or pthreads, and runs on a copy of the site with none of production's data or services ([architecture](https://developer.wordpress.org/playground/developers/architecture/wordpress/); [limitations](https://wordpress.github.io/wordpress-playground/limitations/), undated and possibly stale on Fibers). A green preview catches parse errors and fatals. It does not prove production is safe. Telex already runs this flow (generate, Playground preview, ZIP), and keeps preview state separate from source ([TechCrunch](https://techcrunch.com/2025/09/02/wordpress-shows-off-telex-its-experimental-ai-development-tool/); [Automattic](https://automattic.com/for-agencies/blog/from-concept-to-production-10-tips-for-building-custom-wordpress-blocks-with-telex-ai)). For a "privately hosted" product there is one more issue: loading Playground from playground.wordpress.net hands plugin source to a third-party CDN, so self-host the bundle. Whether an iframe embedded under wp-admin needs COOP/COEP headers is unconfirmed.

A **shadow-slug preview** copies the plugin to `foo--alpaca-preview-<id>/` and swaps it into `option_active_plugins` from a mu-plugin for requests carrying an HMAC'd, admin-bound cookie. Recovery mode uses the same cookie-scoped pattern ([Recovery mode](https://make.wordpress.org/core/2019/04/16/fatal-error-recovery-mode-in-5-2/)). It is cheap, but it is **not a sandbox**: the code runs in production PHP against the production database, activation hooks and cron included. Full clones (WP Staging, a multisite sub-site, a WP Harness container) isolate data at the cost of disk and copy time. Inside one PHP-FPM pool, `open_basedir` and `disable_functions` are hardening, not a jail. No primary source on bypasses was gathered, so treat that as engineering judgment. Pre-flight checks such as `token_get_all()` or nikic/php-parser can catch parse errors and flag `eval`, backticks, `system`, `base64_decode`+`eval` and new outbound URLs, but they are heuristics. The lower-risk product shape is what WPCode and Code Snippets already ship: AI code lives as **snippets** loaded by the host plugin. They are test-run on activation, auto-deactivate on a fatal, and can be disabled with a safe-mode URL (`?wpcode-safe-mode=1`). Editing third-party plugin files stays out of scope ([WPCode docs](https://wpcode.com/docs/how-to-debug-php-errors-in-wpcode/); [Code Snippets](https://codesnippets.pro/blog/recover-wordpress-site-after-snippet-error/)).

### Which editor fits wp-admin

**CodeMirror 6** fits wp-admin best. Secondary estimates put it at about 50–200 kB against Monaco's 2–5 MB ([PkgPulse](https://www.pkgpulse.com/guides/monaco-editor-vs-codemirror-6-vs-sandpack-in-browser-2026)). Replit measured Monaco and related libraries at **5.01 MB** parsed and gzipped and moved to CodeMirror ([Replit](https://replit.com/blog/codemirror)), and Sourcegraph migrated off Monaco for modularity ([Sourcegraph](https://sourcegraph.com/blog/migrating-monaco-codemirror)). The pieces Alpaca Bot needs are a merge view of the agent's diff against the current file and PHP highlighting, which CM6 provides as `@codemirror/merge` and `@codemirror/lang-php` (not re-verified this session). Core still ships CodeMirror **5** through `wp_enqueue_code_editor()`, updated in January 2026, and maintainers want v5 current before any v6 move. No v6 ticket exists ([Trac #48456](https://core.trac.wordpress.org/ticket/48456); [changeset 61611](https://core.trac.wordpress.org/changeset/61611)), so Alpaca Bot would bundle its own CM6. Monaco makes sense only if VS Code ergonomics matter more than payload. Real PHP intellisense needs a language server process bridged over WebSocket either way, which shared hosting will not run. **code-server, openvscode-server and Theia** are separate Node services. code-server asks for at least 1 GB RAM and 2 cores, plus WebSockets and its own auth ([code-server requirements](https://coder.com/docs/code-server/requirements)). They belong only in a self-hosted or dev-container tier behind a reverse proxy that checks wp-admin auth, and their terminal is a shell as the web user. No sourced requirements were found for openvscode-server or Theia specifically. Playground's role is preview runtime, not editor.

## Patterns that map onto a WordPress plugin

| Pattern | Seen in | WordPress mapping |
| --- | --- | --- |
| Declarative, file-based extensions (Markdown + frontmatter) | Claude Code, Codex, opencode, pi | Toolkits and skills as `SKILL.md`-style files in a companion plugin dir or a CPT; Agent Skills frontmatter for portability |
| Namespace every component under its package; validator CLI | Claude Code | Require an `alpaca/<companion>/…` ability namespace; ship `wp alpaca-bot validate` |
| Progressive disclosure under a token budget | Claude Code (1,536 chars), Codex (2% of window) | List abilities and skills by name and description only; load bodies and schemas on demand; cap the index |
| Deferred / code-mode tool exposure | pi (`codemode`, `deferred`), Claude Code tool search, MCP Adapter meta-tools | Per-toolkit exposure tiers (direct, deferred, hidden); discover, get-info, execute meta-tools |
| Pre-tool hook that can deny or rewrite input | Claude Code `PreToolUse`, Codex, opencode `execute.before`, pi `tool_call` | `wp_pre_execute_ability` + `wp_ability_normalize_input` (7.1); own dispatch filter on 6.9/7.0 |
| Post-tool hook / result redaction | All four | `wp_ability_execute_result`, `wp_after_execute_ability` |
| Policy hooks fail closed | Claude Code `onFailure: "block"`; lesson from fail-open defaults | Catch exceptions in guard filters and return `WP_Error` (deny) |
| deny > ask > allow rules, deny-only admin policy layer | Claude Code, opencode `policies` | Rules keyed on ability name + argument pattern in site options; network-admin policy that only tightens |
| Two axes: capability tier vs when to ask | Codex sandbox mode × approval policy | Capability tier (read, edit-content, admin) × approval mode (on-request, never, per-category) |
| Protected paths the agent cannot edit | Codex (`.git`, `.codex`), Claude Code sandbox | Never-touchable options, roles/users, active plugin list, Alpaca Bot's own settings |
| Trust gate for third-party config | Codex, Claude Code, pi `project_trust` | Companion toolkits inert until an admin enables them; never auto-trust in cron or WP-CLI runs |
| Destructive annotation forces approval | Codex MCP | Enforce on `meta.annotations.destructive` yourself; treat third-party annotations as hints |
| Auto-review agent that fails closed | Codex `auto_review` | Optional reviewer model for unattended runs; deny on timeout or parse error |
| Pending permission as an API object + reply endpoint | opencode 2.0 server | REST `GET pending` / `POST reply` for approvals; "always" writes a scoped allow rule |
| Receipts / audit trail | Codex rollouts, opencode durable log | `wp_ability_invoked` + `wp_ability_permission_result` + `wp_after_execute_ability` records; optional `log_ai_request()` bridge |
| Append-only session tree with branches | pi JSONL, Codex rollouts | Conversation table with `parent_id`; active-branch context; fork and resume |
| Compaction as "handoff summary", explicit re-injection set | Codex prompt, Claude Code, opencode `compaction` agent | Cheap summarizer model; re-inject site instructions, active toolkit list, plan |
| Spill large tool output to storage with a preview | Claude Code (25k tokens / 50k chars) | Store oversized results as an attachment or transient; send preview + handle |
| Subagent returns only a summary | Claude Code, opencode background agents | Action Scheduler job that runs a sub-conversation and returns a summary |
| Last step strips tools | opencode `steps` | Max-turns cap; final turn without tools forces a summary |
| `{content, details}` tool result split | pi | Ability output = model-facing content; receipt/UI metadata kept separately |
| One engine, many clients | All four | One loop behind admin chat, front-end chat, REST, WP-CLI and MCP |
| Headless mode with JSON events + schema output | Codex `exec`, Claude Code `-p` | `wp alpaca-bot run --format=json --schema=…` and a REST equivalent |
| Volatile live stream + durable replayable log | opencode 2.0 | Polling or SSE for live, stored event log as source of truth |
| Context-anchored patch format | Codex `apply_patch` | Diff-based edit tool for post content and code; reviewable in a CM6 merge view |
| Checkpoints / undo before writes | Claude Code `/rewind`, opencode snapshots | Revisions for posts; explicit option/table snapshots before write abilities |
| Packages from npm/git with pinning | Claude Code marketplaces, pi packages, opencode | Companion plugins on wp.org with `Requires Plugins: alpaca-bot`; runtime API-version check |
| First-party extensions packaged as removable plugins | pi built-ins, Codex bundled skills | Ship first-party toolkits as standalone companion plugins to avoid the long-tail-quality problem |
| Typed user config prompted on enable | Claude Code `userConfig` | Companion settings schema rendered by the host; secrets stored encrypted |
| Zero-cost default sign-in / local model | Codex ChatGPT sign-in, opencode Ollama probe | Ollama auto-detect plus Connectors-provided keys as the default path |
| Shared model catalog with capability flags | opencode models.dev | Catalog with context window, cost and tool-support flags; tools off for weak local models |
| Evals and staged rollout for harness changes | Anthropic postmortem | Eval suite on system-prompt and default changes; deprecate with `apply_filters_deprecated` |
| Agent extends itself (write, reload, test) | pi | Out of scope on production; only in Playground or a staging clone |

## Conclusion

The harness market has done Alpaca Bot's design work, and WordPress 7.1 has done much of the implementation. The most valuable insight is that **core's ability lifecycle filters are a cross-agent harness API**. Guardrails, approvals and receipts built on `wp_pre_execute_ability`, `wp_ability_permission_result` and `wp_ability_invoked` govern every agent on the site, including the AI plugin's coming Site Agent and any external MCP client, not just Alpaca Bot's chat. That makes "the governance layer for all WordPress agents" a sharper position than "another chatbot". It conflicts with the current 6.9 floor, so the decision to make is whether a 6.9/7.0 fallback dispatch layer is worth carrying or whether 7.1 becomes the next floor bump. Per the repo's own versioning notes, that bump moves together with `Requires PHP` and `Tested up to` or not at all. The distribution evidence points the same way: a public, Agent-Skills-compatible repo of toolkits and a documented companion contract are likely to do more for adoption than any single feature.

On live editing, the harnesses offer no safety the WordPress record does not already contradict. Their sandboxes get escaped, their hooks fail open, and their own docs disclaim prompts as a boundary. The practical line for Alpaca Bot is a snippet store first and a staged, approve-by-hash file pipeline second. Use a Playground preview and a fail-closed loopback, keep the feature unreachable from any conversation that has read untrusted content, and degrade to "propose a diff" wherever the host or `DISALLOW_FILE_*` says no. Full in-browser IDEs belong to the dev-container tier, not to wp-admin on a shared host.
